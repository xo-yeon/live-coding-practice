# 리팩터링 판단 근거

## 가독성

- 한 번에 이해해야 하는 맥락을 줄이고 복잡한 조건에 의도를 드러내는 이름을 붙인다.
- 구현 세부사항을 필요한 경계에서 분리해 위에서 아래로 읽히게 한다.
- 함수와 변수 이름이 실제 동작을 설명하는지 확인한다.

## 예측 가능성

- 이름과 실제 동작, 같은 종류 함수의 반환 타입을 일치시킨다.
- 숨은 부수 효과를 제거하고 상태 전환과 에러 처리를 명시적이고 일관되게 만든다.

## 응집도

- 함께 변경되는 코드와 관련 상태·동작을 함께 둔다.
- 비즈니스 규칙과 검증 규칙을 한 변경에서 빠뜨리지 않도록 관리한다.

## 결합도

- 한 부분을 수정했을 때 영향 범위를 제한한다.
- UI와 계산, 서버 상태와 클라이언트 상태를 구분하고 외부 API 세부사항을 격리한다.
- 불필요한 전역 상태를 제거한다.

함수를 무조건 잘게 나누거나 중복을 무조건 공통화한다고 좋은 코드가 되지는 않는다. 짧고 명확한 중복이 과도한 추상화보다 나을 수 있다. 라이브 코딩에서는 전체 재설계보다 사용자 결과에 영향을 주는 고위험 문제를 먼저 해결한다. 코드 스타일보다 실제 버그를 우선하고, 수정 전 동작을 확인한 뒤 테스트나 수동 검증으로 변경을 증명한다.
