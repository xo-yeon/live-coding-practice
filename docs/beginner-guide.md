# 좋은 코드 판단부터 연습하기

처음에는 “이 코드가 깔끔한가?”보다 “요구한 결과가 나오는가?”를 먼저 확인합니다.
문제가 보이지 않는다고 실패한 것이 아닙니다. 입력 하나를 넣고 결과를 설명하는 것부터 시작합니다.

## 판단할 기준

- 정확성: 요구사항대로 동작하는가?
- 예측 가능성: 호출하거나 클릭했을 때 예상하지 못한 변화가 없는가?
- 이해하기 쉬움: 값이 어디에서 오고 언제 바뀌는지 설명할 수 있는가?
- 검증 가능성: 입력과 기대 결과를 작은 테스트로 확인할 수 있는가?

state가 많다고 반드시 나쁘지는 않습니다. 서로 독립적으로 변하는 UI 값은 각각 state가 필요할 수 있습니다.
다른 값에서 계산할 수 있는 정보를 따로 저장한다면, 두 값이 늘 일치해야 한다는 관리 부담이 생기는지 살펴봅니다.

ref는 값을 기억하지만 current를 바꿔도 화면을 다시 그리지 않습니다.
화면이 즉시 반영해야 하는 값은 state가 자연스럽고, 타이머 ID·DOM 참조처럼 렌더링과 직접 관계없는 값에는 ref가 어울립니다.
제출할 때만 읽는 uncontrolled input은 ref로 다룰 수도 있습니다. 입력값에 따라 화면 표시가 바뀌는지까지 고려해야 합니다.
state를 ref로 바꾸는 것 자체는 개선의 근거가 아닙니다.

## 지금 할 연습

1. 01 거래 합계: TypeScript 함수 하나, 권장 15분.
2. 02 생활비 예산 입력: 작은 React 컴포넌트 하나, 권장 20분.
3. 03 받는 분 선택: 검색과 선택이 있는 React 컴포넌트 하나, 권장 25분.

세 문제 모두 Level 1이며 처음에는 시간을 재지 않아도 됩니다.
각 문제에 공개 테스트 2개가 있습니다. 시작 코드에서도 통과하며, 모든 요구사항을 검증하지는 않습니다.
실패하는 입력을 발견하면 그 행동을 테스트로 추가하고 코드를 고친 뒤 다시 실행합니다.
테스트 작성법이 낯설면 AI에게 별개의 예제로 작성법을 설명해 달라고 요청할 수 있습니다.

메모는 “입력 / 기대 결과 / 실제 결과 / 수정 이유 / 확인 방법” 다섯 줄이면 충분합니다.
첫 단계에서는 점수보다 이 다섯 가지를 말할 수 있는지 확인합니다.
이후 Level 2의 2~4개 파일로 늘리고, 마지막에 기존 송금 예약 관리 60분 과제를 진행합니다.
