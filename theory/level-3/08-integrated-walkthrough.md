# 08. 종합 코드 해설: 워크숍 예약 변경

이 수업은 Level 1~2의 판단을 연결합니다. 실제 시험 크기를 흉내 내기 위해 파일을 늘리기보다, 서로 다른 책임이 연결되는 원리를 학습합니다. 완성 코드는 [examples](../examples/)에 있으며 처음부터 읽어도 됩니다.

## 공개된 제품 계약

- 최초 확정 좌석은 2석이며 1석은 15,000원입니다.
- 입력은 1~20 정수이고 저장 버튼으로 확정합니다.
- 저장 중에는 편집과 추가 제출을 받지 않습니다.
- 성공 응답의 좌석 수를 확정값과 입력에 반영합니다.
- 실패하면 기존 확정값과 사용자의 초안을 유지하고 오류를 보여줍니다.
- 가상 API는 200ms 후 응답하며, 13석 요청은 실패합니다.

가상 서버에는 실제 재고·인증·결제·영구 저장이 없습니다. `saveSeats`는 유효한 확정 좌석 수를 반환한다는 계약입니다. 실제 HTTP API로 바꿀 때는 응답 검증을 API 경계에 추가합니다.

## 먼저 비교할 Before

다음은 앞선 수업에서 배운 문제를 한곳에 모은 설명용 발췌입니다. 현재 실행 예제는 개선된 버전입니다.

```tsx
async function submit() {
  setConfirmed(Number(raw));
  setSaving(true);
  await saveSeats(Number(raw));
  setSaving(false);
}
```

입력이 비어 있으면 0을 보낼 수 있습니다. 성공 전 확정값이 바뀌고, 거절되면 마지막 줄까지 도달하지 못해 저장 중 상태가 남습니다. 요청이 진행 중인데 재진입을 막는 장치도 없습니다.

이 문제들은 모두 “나쁜 코드”라는 이름으로 묶기보다 입력 계약 위반, 서버와 화면의 불일치, 실패 후 복구 불가, 중복 요청으로 구분합니다.

## After를 사건 순서로 읽기

1. 입력 이벤트는 `changeRaw`를 호출합니다. 저장 중이면 무시하고, 그 외에는 초안과 기존 오류만 바꿉니다.
2. 제출은 잠금을 확인하고 `parseSeats`를 실행합니다. 실패하면 오류를 표시하고 API를 호출하지 않습니다.
3. 유효한 입력이면 즉시 잠금을 잡고 저장 중 화면을 표시합니다. 확정값은 그대로 둡니다.
4. 서버 성공이면 반환값을 `confirmed`와 `raw`에 반영합니다.
5. 서버 실패이면 오류만 표시합니다. 초안과 확정값을 변경하지 않습니다.
6. 어느 경로든 `finally`에서 잠금을 풀고, 화면이 살아 있다면 저장 중 표시를 끝냅니다.

```text
확정 2 / 초안 "2"
  → 초안 "4" 입력: 확정은 여전히 2
  → 저장: 입력·버튼 비활성화
  → 실패: 확정 2 / 초안 "4" / 오류 표시
  → 재시도: 이전 오류 제거
  → 성공 4: 확정 4 / 초안 "4" / 버튼 활성화
```

## 상태가 각각 필요한 이유

`raw`는 아직 유효하지 않을 수 있는 편집 문자열입니다. `confirmed`는 서버가 확정한 숫자입니다. 서로 의미가 달라 두 값이 필요합니다. 총금액은 `confirmed * 15000`으로 계산하므로 별도 state를 만들지 않습니다.

`saving`은 화면을 갱신하기 위한 state이고 `lock`은 같은 호출 스택에서도 즉시 중복 제출을 막기 위한 ref입니다. `mounted`는 화면이 사라진 뒤 결과를 반영하지 않기 위한 ref이며 네트워크나 서버 작업을 취소하지는 않습니다.

이 Hook은 같은 컴포넌트에 새 `initialSeats`가 들어온다고 초안을 자동으로 덮지 않습니다. 초기값은 편집 세션 시작값입니다. 다른 예약을 선택하면 부모가 `key={reservation.id}`로 새 편집 세션을 만들도록 정했습니다. 같은 예약을 서버에서 재조회했을 때 초안과 충돌하는 정책은 확장 과제입니다.

## 왜 지금 이 정도로만 분리했나

입력 검증은 React 없이 테스트할 수 있도록 함수로 분리했습니다. API는 테스트에서 교체할 수 있도록 전달하고, Hook은 저장 생명주기를 모았습니다. UI의 단순한 라벨마다 별도 파일을 만들지는 않았습니다.

작은 제품에서는 Hook까지 분리하지 않고 화면에 두어도 타당합니다. 이 교재에서는 상태 전이를 따로 읽고 직접 호출해 검증하기 위해 분리했습니다. 같은 구조를 모든 코드에 강제하지 않습니다.

## 테스트 읽고 실행하기

```bash
pnpm exec vitest run --config theory/vitest.config.ts
pnpm exec tsc -p theory/tsconfig.json
```

성공 테스트는 완료 전과 완료 후를 모두 검사합니다. 실패 테스트는 오류 표시에서 멈추지 않고 재시도까지 진행합니다. 중복 진입 테스트는 비활성화된 버튼을 두 번 클릭하는 대신 같은 렌더의 제출 함수를 연속 호출하여 잠금의 보장 범위를 확인합니다.

브라우저용 페이지는 연결하지 않았습니다. 컴포넌트 테스트가 UI를 jsdom에서 렌더하고 입력·제출을 실행합니다. jsdom은 테스트용 DOM 환경이며 실제 브라우저의 레이아웃·네트워크·접근성 전체를 보장하지 않습니다.

## 변형 질문과 해설

**질문:** 저장 중 편집을 허용하고 싶다면 disabled만 지우면 되는가?

**해설:** 성공 시 `setRaw(String(saved))`가 사용자가 그 사이 새로 쓴 초안을 덮을 수 있습니다. 제출 시점 초안을 별도로 기억하고, 그 이후 편집이 없을 때만 초안을 갱신하는 등 새 정책이 필요합니다. UI 요구사항 변경이 상태 모델에 영향을 주는 사례입니다.

**면접 답변:** “서버 확정값과 입력 초안을 분리했고 저장 중 편집을 막는 계약을 사용했습니다. 편집을 허용하는 정책으로 바뀌면 성공 응답이 새 초안을 덮지 않도록 추가 설계가 필요합니다.”
