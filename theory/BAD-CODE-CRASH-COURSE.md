# 못 짠 코드를 판별하고 고치는 법 — ㅇReact·TypeScript 속성 교재

목표는 코드를 보고 **어떤 조건에서 문제가 생기는지, 사용자가 무엇을 잘못 경험하는지, 왜 이 수정이 필요한지** 설명하는 것입니다. 금융·광고 지식은 필요하지 않습니다. 목록 검색, 상세 편집, 저장 같은 일반적인 화면을 사용합니다.

사용자가 전달한 면접 방식인 ‘코드를 1시간 전에 받아 파악한 뒤, 근거를 설명하며 해결·개선하기’에 맞춘 자체 교재입니다. 특정 문제가 실제로 출제된다는 뜻은 아닙니다. 사전 읽기 60분과 실제 면접 시간은 따로 관리합니다.

**시간이 없으면:** 0장과 1~5장의 원인·재현·검증을 먼저 읽으세요. 이후 9장의 종합 해설과 10장의 사전 읽기 절차를 봅니다. 6~8장은 입력·구조·성능을 보완하는 내용입니다. 모든 코드를 외울 필요는 없습니다.

코드는 서로 독립적인 수업 발췌입니다. React import, 타입, API, JSX 일부는 생략했습니다. Before와 After는 대안이며 한 파일에 함께 붙여 실행하지 않습니다. 기존 연습 문제의 비공개 해설과 무관합니다.

## 0. ‘못 짰다’고 판단하기 전에 세 가지로 나누기

| 분류 | 예시 | 판단 근거 | 대응 |
| --- | --- | --- | --- |
| 실제 동작 결함 | 저장 실패했는데 성공으로 표시 | 요구사항과 실제 결과가 다름 | 재현하고 우선 수정 |
| 변경하기 어려운 구조 | 같은 허용 조건이 버튼과 안내에 따로 존재 | 정책 변경 때 일부만 바뀔 위험 | 필요한 범위에서 구조 개선 |
| 취향·형식 차이 | 함수 선언 방식, 파일 이름 취향 | 동작이나 변경 비용의 근거가 아직 없음 | 기존 규칙을 따르고 후순위 |

긴 함수, 많은 state, useEffect, ref, 중복 코드가 있다는 사실만으로 결함은 아닙니다. **이 코드 때문에 어떤 상황에서 무엇이 틀리는가?**에 답할 수 있어야 합니다.

예를 들어 `key={index}`를 발견했다고 바로 버그라고 단정하지 않습니다. 목록이 재정렬·삭제되고 행에 입력 상태가 있는지 확인합니다. 그런 조건이 있을 때 다른 항목에 입력값이 붙는 재현을 만들 수 있습니다.

판단은 다음 문장으로 연결합니다.

> “현재 [조건]에서 [실제 동작]이 발생합니다. 요구사항은 [기대 동작]이므로 [사용자 영향]이 있습니다. 원인은 [데이터·상태·요청 흐름]이며, [수정] 후 [검증]하겠습니다.”

‘분리하면 깔끔하다’보다 ‘버튼과 안내가 같은 판정 결과를 사용하게 해서 조건 불일치를 막는다’가 확인 가능한 설명입니다.

## 1. 원본을 직접 바꾼다 — 참조와 불변성

**단서:** state나 props 배열에 `push`, `splice`, `sort`를 호출하거나 객체 필드에 직접 대입합니다.

```tsx
// Before: items는 React state
items[0].done = true;
setItems(items);
```

**왜 문제인가:** 내용은 바뀌었지만 배열은 같은 객체입니다. React가 같은 값으로 판단해 갱신을 건너뛸 수 있고, 다른 코드가 참조하던 이전 데이터까지 바뀝니다. 항상 화면이 멈춘다고 단정하지 말고 다른 렌더가 우연히 문제를 가리고 있는지도 봅니다.

```tsx
// After: 변경할 배열과 항목을 새로 만든다
setItems((previous) =>
  previous.map((item) =>
    item.id === targetId ? { ...item, done: true } : item,
  ),
);
```

새 배열만 만들고 그 안의 객체를 직접 바꾸면 객체 참조는 여전히 공유합니다. 위 코드는 바꿀 항목도 새로 만듭니다. `previous`를 받는 함수형 업데이트는 이전 상태에서 다음 상태를 계산할 때 사용합니다. 모든 setter에 무조건 필요한 형식은 아닙니다.

**재현·검증:** 완료 버튼을 누르면 해당 항목만 바뀌는지, 다른 항목은 유지되는지 확인합니다. 순수 변환 함수라면 입력 객체가 바뀌지 않았는지도 검사합니다. props 목록 정렬은 `[...items].sort(...)`처럼 사본에서 수행할 수 있습니다. [React 배열 갱신](https://react.dev/learn/updating-arrays-in-state)

**반례:** 함수 안에서 막 만든 배열을 반환 전에 `push`로 채우는 것까지 잘못은 아닙니다. 이미 공유된 state·props를 변경하는지가 핵심입니다.

## 2. 같은 사실을 두 군데 저장한다 — 원본과 파생값

**단서:** 전체 목록과 필터된 목록, 선택 ID와 선택 개수처럼 계산 가능한 값을 각각 state로 두고 Effect로 맞춥니다.

```tsx
// Before
const [keyword, setKeyword] = useState('');
const [visible, setVisible] = useState(items);
useEffect(() => {
  setVisible(items.filter((item) => item.name.includes(keyword)));
}, [keyword]); // items가 바뀌는 경우를 빠뜨림
```

**문제 상황:** 검색어는 그대로인데 새 목록을 받으면 화면의 visible은 옛 목록입니다. 동기화해야 할 원본이 둘이 되어 변경 경로를 놓치기 쉽습니다.

```tsx
// After: 표시할 때 현재 입력으로 계산
const visible = items.filter((item) => item.name.includes(keyword));
```

이렇게 하면 목록과 검색어가 바뀔 때 같은 렌더에서 결과를 계산합니다. 계산이 실제로 비싸면 측정 후 `useMemo`를 검토합니다. 단순 계산을 정확하게 만들기 위해 useMemo가 필요한 것은 아닙니다. [React의 불필요한 Effect 줄이기](https://react.dev/learn/you-might-not-need-an-effect)

**재현·검증:** 검색어를 유지한 채 목록을 교체하고 새 결과가 나오는지 확인합니다. 검색어 삭제, 결과 0건도 봅니다.

**반례:** 상세 편집 초안은 서버 값과 잠시 달라져야 하는 정보입니다. 독립적인 사용자 의도가 있으므로 별도 state가 타당합니다. 단순 복사와 의도적인 초안을 구분하세요.

## 3. 다른 항목의 상태가 섞인다 — ID·key·초안의 소속

**단서:** 변경 가능한 목록에 index key를 쓰거나, 선택 항목이 바뀌는데 같은 폼 state를 유지합니다.

```tsx
// Before
function Editor({ item }: Props) {
  const [name, setName] = useState(item.name);
  const save = () => api.save({ id: item.id, name });
  // 입력 UI 생략
}
```

**문제 상황:** A에서 이름을 입력한 뒤 B를 선택하면 props의 ID는 B인데 name은 A에서 쓰던 값일 수 있습니다. useState의 초기값은 props가 바뀔 때마다 기존 state를 다시 초기화하지 않습니다.

```tsx
// After의 한 선택: 항목마다 새 편집 세션
// 부모에서 미저장 변경의 폐기 확인을 마친 뒤 selected를 바꾼다.
<Editor key={selected.id} item={selected} />
```

계정별로 같은 ID가 가능하면 계정도 식별에 포함합니다. 미저장 내용을 보존하면서 이동해야 한다면 항목별 초안을 상위에서 보관하는 다른 정책이 필요합니다. key를 바꾸면 해당 하위 state는 초기화되므로 확인 없이 사용하면 입력을 잃습니다.

행의 `key={item.id}`도 같은 원리로 항목의 정체성을 유지합니다. index는 항목이 아니라 위치이므로 삭제·정렬 뒤 state가 다른 행에 붙을 수 있습니다. [React 목록의 key](https://react.dev/learn/rendering-lists)

**재현·검증:** A 편집 → B 선택, 이동 취소, 목록 첫 행 삭제, 정렬 변경을 확인합니다. 같은 A의 재조회로 미저장 입력이 지워지지 않는지도 봅니다. “props가 바뀌면 항상 입력을 복사하는 Effect”는 이 마지막 경우를 망가뜨릴 수 있습니다.

## 4. 먼저 보낸 요청이 나중 화면을 덮는다 — 비동기 순서

**단서:** 조건마다 요청하고 응답을 무조건 `setState`합니다.

```tsx
// Before
useEffect(() => {
  api.search(keyword).then(setRows);
}, [keyword]);
```

**재현:** `a` 검색을 느리게, 바로 뒤의 `ab` 검색을 빠르게 만듭니다. `ab` 결과가 나온 뒤 `a`가 덮으면 검색어와 결과가 서로 다릅니다. “마지막에 도착한 응답”과 “현재 조건에 맞는 응답”은 다릅니다.

```tsx
// After 발췌: view는 key/status/data를 갖는 조회 상태라고 가정
useEffect(() => {
  let active = true;
  setView({ key: keyword, status: 'loading' });
  api.search(keyword).then(
    (data) => {
      if (active) setView({ key: keyword, status: 'success', data });
    },
    () => {
      if (active) setView({ key: keyword, status: 'error' });
    },
  );
  return () => { active = false; };
}, [keyword]);

const visible = view.key === keyword
  ? view
  : { key: keyword, status: 'loading' };
```

각 Effect는 자기 active를 갖습니다. 이전 실행을 정리하면 이전 성공·실패가 모두 화면을 바꾸지 못합니다. 마지막 key 비교는 새 Effect가 실행되기 전 렌더에서도 이전 조건의 결과를 숨깁니다. [React Effect와 조회 정리](https://react.dev/reference/react/useEffect)

**한계:** 예제 API는 Promise를 반환하고 응답을 거절로 분류한다고 가정합니다. 같은 조건에서 재시도하는 기능은 별도 트리거가 필요합니다. 계정·페이지도 결과를 바꾸면 조회 식별에 포함합니다. 이미 조회 라이브러리가 있다면 그 key와 상태를 올바르게 사용하는 것이 더 작은 수정일 수 있습니다.

**검증:** B 성공 뒤 A 성공, B 성공 뒤 A 실패를 모두 검사합니다. debounce는 요청 빈도를 줄일 뿐 이미 시작된 응답의 순서를 보장하지 않습니다. 취소도 서버 작업의 되돌림을 뜻하지 않습니다.

## 5. 실패했는데 성공처럼 보인다 — 저장과 오류 복구

**단서:** 성공 전에 입력을 지우거나, catch가 없거나, 실패하면 loading이 계속 true입니다.

```tsx
// Before
setSaving(true);
setConfirmedName(draft);
setDraft('');
await api.saveName(draft);
setSaving(false);
```

**문제 상황:** 서버가 거절하면 저장된 적 없는 이름이 확정값으로 보이고 초안도 사라집니다. 마지막 setter가 실행되지 않아 다시 저장할 수 없을 수 있습니다.

```tsx
// After: 저장 중 입력·대상 이동을 잠그는 편집기라고 가정
// savingRef는 useRef(false), API는 성공 확정값을 반환한다.
async function save() {
  if (savingRef.current) return;
  savingRef.current = true;
  setSaving(true);
  setError(null);
  const submitted = { id: item.id, name: draft };
  try {
    const saved = await api.save(submitted);
    setConfirmedName(saved.name);
    setDraft(saved.name);
  } catch {
    setError('저장 결과를 확인하지 못했습니다. 입력은 유지됩니다.');
  } finally {
    savingRef.current = false;
    setSaving(false);
  }
}
```

성공에만 확정값을 갱신하고, finally에서 성공·실패 모두 잠금을 해제합니다. ref는 동일 핸들러가 렌더 반영 전에 재진입해도 잠그려는 용도입니다. 버튼에는 saving으로 disabled를 표시합니다. 이미 mutation 계층이 이 수명주기를 관리한다면 상태·잠금을 불필요하게 이중 구현하지 않습니다.

**중요한 조건:** 저장 중 이동이나 추가 입력을 허용한다면 이 발췌만으로 부족합니다. 응답을 제출한 ID에 적용하고 제출 후 작성한 새 초안은 지우지 않아야 합니다. 서버가 적용했지만 응답만 끊긴 상황은 결과 불명일 수 있으므로 무조건 실패라고 단정하거나 자동 재전송하지 않습니다.

**검증:** 정상 저장, 명시적 거절, 실패 후 다시 저장, 연속 호출을 확인합니다. 요청이 두 번 보였다고 실제 데이터도 두 번 생성됐다고 단정하지 않고 서버 계약을 확인합니다.

### 오류 처리에서 같이 확인할 세 가지

- `fetch`는 HTTP 500이라고 자동 reject하지 않습니다. API 계층에서 `response.ok` 등을 검사해야 합니다.
- `catch { return []; }`는 장애를 ‘결과 없음’으로 숨길 수 있습니다. 빈 결과와 실패의 화면을 구분합니다.
- Suspense는 모든 Promise를 감지하지 않고, Error Boundary도 일반 이벤트의 비동기 오류를 자동으로 모두 잡지 않습니다. 저장 오류는 실제 전달 경로에서 처리해야 합니다. [React Suspense](https://react.dev/reference/react/Suspense), [Error Boundary](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)

## 6. 타입과 실제 입력을 혼동한다 — 런타임 검증

**단서:** `as number`, `as User`, `!`만으로 안전하다고 생각하거나 `Number(raw)`만 사용합니다.

```ts
// Before: 좌석 수는 1~10 정수라는 요구사항
const seats = Number(raw);
if (!seats) return;
await reserve(seats);
```

빈 문자열은 0이 되고, -1이나 1.5는 참으로 평가되어 통과합니다. “숫자로 변환된다”와 “허용된 입력이다”는 다릅니다.

```ts
// After: 표기와 값의 범위를 명시적으로 검사
function parseSeats(raw: string): number | null {
  const text = raw.trim();
  if (!/^\d+$/.test(text)) return null;
  const value = Number(text);
  return Number.isSafeInteger(value) && value >= 1 && value <= 10
    ? value
    : null;
}
```

이 예제는 숫자로만 된 정수 표기와 앞뒤 공백을 허용합니다. `1e1` 같은 표기를 허용할지는 제품 요구에 따라 정합니다. 실패값을 0과 혼동하지 않도록 null을 사용합니다.

`response as User`는 서버 응답을 검사하거나 변환하지 않습니다. 필요한 필드의 실제 타입과 누락 여부는 외부 데이터 경계에서 검사해야 합니다. TypeScript는 주로 실행 전 정적 검사를 하며 런타임 데이터를 보증하지 않습니다.

**검증:** 빈 값, 공백, -1, 0, 1, 10, 11, 1.5, 문자 입력을 확인합니다. 모든 요구사항에 없는 거대한 검증 프레임워크를 새로 도입할 필요는 없습니다.

## 7. 조건과 책임이 흩어져 있다 — 근거 있는 리팩터링

**단서:** 동일 정책이 여러 곳에 복사되어 있거나 함수 이름과 실제 효과가 다릅니다.

```ts
// Before: 같은 예약 가능 여부를 서로 다르게 판단
const disabled = status !== 'OPEN' || remaining < seats;
const message = status === 'CLOSED' ? '예약 종료' : '예약 가능';
```

잔여석보다 많이 신청하면 버튼은 막히는데 안내는 예약 가능입니다. 이 경우의 개선 이유는 중복 제거 자체가 아니라 **하나의 정책에 대한 UI 불일치**입니다.

```ts
// After: seats는 앞 장의 검증을 통과했다고 가정
function getReservationDecision(
  status: 'OPEN' | 'PAUSED' | 'CLOSED', remaining: number, seats: number,
) {
  if (status !== 'OPEN') return { allowed: false, message: '예약 불가 상태' };
  if (remaining < seats) return { allowed: false, message: '잔여석 부족' };
  return { allowed: true, message: '예약 가능' };
}
// 버튼은 !decision.allowed, 안내는 decision.message를 사용
```

**검증:** OPEN+충분, OPEN+부족, PAUSED, CLOSED에서 버튼과 안내가 같은 판단인지 확인합니다. 서버도 실제 잔여석을 검사해야 하며 프론트 판정이 예약 성공을 보장하지는 않습니다.

### 어디로 분리할지 정하는 기준

| 로직 | 우선 고려할 위치 | 분리 이유 |
| --- | --- | --- |
| 계산·검증·허용 여부 | 일반 함수 | React 없이 입력·출력 검증 가능 |
| 조회 구독·초안·저장 흐름 | Hook 또는 해당 컴포넌트 | 관련 상태 수명주기를 함께 읽음 |
| 의미 있는 UI 영역 | 컴포넌트 | 호출부에서 표현 목적을 파악 |
| 통신·HTTP 오류·응답 검사 | API 계층 | 외부 계약을 일관되게 처리 |

커스텀 훅은 상태 로직을 재사용합니다. 호출한 컴포넌트들의 지역 state를 자동 공유하지 않습니다. 컴포넌트가 길다는 이유만으로 `useEverything`에 옮기면 책임 혼합은 그대로일 수 있습니다.

Frontend Fundamentals의 네 관점은 이렇게 질문으로 바꿉니다. “이해하려고 읽을 맥락이 줄었나(가독성)? 이름대로 동작하나(예측 가능성)? 함께 바뀔 것이 모였나(응집도)? 무관한 코드까지 바꾸게 되나(결합도)?” [공식 코드 품질 기준](https://frontend-fundamentals.com/code-quality/code/)

**반례:** 두 화면의 입력 모양만 같고 정책은 다르면 공통화가 오히려 결합을 키웁니다. 짧은 중복을 허용하고 안정적인 계산만 공유할 수 있습니다. 줄 수·훅 개수·파일 개수가 품질 점수는 아닙니다.

## 8. 추가로 빠르게 훑을 문제 상황

아래는 발견 즉시 수정할 목록이 아니라, 재현할 조건을 찾는 표입니다.

| 코드 단서 | 만들어 볼 상황 | 의심 원인·수정 방향 |
| --- | --- | --- |
| Effect에서 쓰는 props가 deps에 없음 | props 변경 후 동작 | 오래된 값을 참조하는지 확인; 의존성 또는 Effect 목적 수정 |
| Effect가 자신이 바꾸는 값에 의존 | 로딩·렌더 반복 관찰 | 순환 갱신 여부 확인; deps를 억지로 지우지 않음 |
| 이벤트·타이머 등록에 cleanup 없음 | 진입·이탈·재진입 | 등록 중복 확인, 해당 리소스 정리 |
| 필터 변경 때 현재 페이지 유지 | 마지막 페이지에서 필터 변경 | 새 결과에 없는 페이지 조회; 함께 1페이지로 변경 |
| 서버 페이지를 브라우저에서만 정렬 | 다음 페이지에 더 큰 값 배치 | 전체 정렬 요구면 서버 정렬 필요 |
| `Promise.all`로 독립 저장 여러 건 | 일부만 거절 | 다른 요청은 자동 취소되지 않음; 개별 결과·복구 표시 |
| 렌더마다 동일한 전체 합계 반복 | 큰 입력으로 계산 측정 | 한 번만 계산; 무조건 memo부터 넣지 않음 |
| loading·success·error가 독립 boolean | 재시도 직후 상태 확인 | 모순 조합이 생기면 상태 union 또는 전이 정리 |

성능은 네트워크 대기, JavaScript 계산, React 렌더·DOM 비용을 나눠 봅니다. useMemo는 동일 입력의 재계산을 줄일 수 있고, 가상화는 화면 밖 DOM 수를 줄입니다. 해결하는 비용이 서로 다릅니다. 작은 화면에 도구를 추가한 사실만으로 개선됐다고 말하지 않습니다.

Suspense 전환, 전역 상태 도입, Worker 도입은 필수 과제가 아닙니다. 현재 결함의 원인을 해결하는 데 필요한지 먼저 판단합니다.

## 9. 종합 해설 — 한 화면에서 문제를 연결해 읽기

상황: 이름을 검색하고, 선택한 사람의 표시 이름을 편집하는 화면입니다. API는 조회 배열과 저장된 사람 객체를 반환하며 실패 시 reject한다고 가정합니다.

```tsx
function PeoplePage() {
  const [keyword, setKeyword] = useState('');
  const [people, setPeople] = useState<Person[]>([]);
  const [selected, setSelected] = useState<Person | null>(null);
  const [name, setName] = useState('');
  const [saving, setSaving] = useState(false);

  useEffect(() => {
    api.search(keyword).then(setPeople);
  }, [keyword]);

  async function save() {
    if (!selected) return;
    setSaving(true);
    await api.save({ id: selected.id, name });
    setSaving(false);
  }

  return (
    <>
      <input aria-label="검색" value={keyword}
        onChange={(e) => setKeyword(e.target.value)} />
      {people.map((person) => (
        <button key={person.id} onClick={() => setSelected(person)}>
          {person.name}
        </button>
      ))}
      <input aria-label="이름" value={name}
        onChange={(e) => setName(e.target.value)} />
      <button disabled={saving || !selected} onClick={save}>저장</button>
    </>
  );
}
```

### 먼저 역할을 설명한다

검색어가 바뀌면 사람 목록을 요청합니다. 행을 클릭하면 저장 대상이 selected에 들어가고, 이름 입력은 별도 name에 저장됩니다. 저장 버튼은 selected.id와 name을 묶어 서버로 보냅니다. 이 설명만으로도 목록 조회와 편집 입력이 서로 다른 수명을 가진다는 점이 보입니다.

### 결함 세 개를 증거로 고정한다

| 재현 | 실제 결과 | 기대 결과·영향 |
| --- | --- | --- |
| A 선택·입력 후 B 선택 | name은 A 입력 그대로, 대상은 B | B 편집 시작값 또는 이동 확인 필요; 다른 사람 수정 위험 |
| 저장 API 거절 | saving이 true로 남고 오류 안내 없음 | 초안 유지·오류 안내·다시 조작 가능 |
| 검색 A를 늦게, B를 빠르게 완료 | 마지막 도착한 A가 목록을 덮음 | 현재 검색 조건과 결과 일치 |

API 요청이 잘못된 ID·이름 조합을 포함한다는 사실은 확인할 수 있습니다. 실제 서버에 반영됐는지는 응답과 저장 계약으로 추가 확인합니다. 코드가 짧거나 보기 좋다는 사실은 이 결함들을 없애주지 않습니다.

### 해결 순서를 정한다

이 예시에서는 잘못된 사람에게 저장되는 경로를 먼저 막습니다. 그다음 실패 후 복구, 조회 순서 처리를 고칩니다. 실제 요구사항과 재현 결과에 따라 순서는 달라질 수 있습니다. 다른 사람을 수정하는 위험과 결과 확인의 어려움이 이 순서의 근거입니다.

### 최소 수정의 범위를 말한다

1. 편집 상태를 선택한 사람의 세션에 귀속시킵니다. 항목별 Editor를 두는 방법이라면 미저장 이동 확인을 먼저 연결합니다.
2. 저장은 성공·실패·finally로 나누고, 예제에서는 저장 중 입력·이동을 막아 응답 적용을 단순하게 합니다.
3. 조회는 조건별 응답 소속을 확인하고 이전 성공·실패를 무시합니다. 검색 실패도 빈 목록과 구분합니다.

이때 새 전역 상태 라이브러리나 범용 폼 프레임워크가 필요한 것은 아닙니다. 책임 분리가 결함 해결에 도움이 되는 범위에서만 구조를 바꿉니다.

### 검증을 설명한다

A→B 전환의 입력값, 저장 거절 뒤 버튼 복구, 실패 후 재시도, 응답 역전과 정상 검색을 확인합니다. 비동기 테스트는 시간을 오래 기다리는 대신 Promise 완료 순서를 직접 제어하면 안정적으로 재현할 수 있습니다.

> “편집 대상과 초안이 따로 바뀌어 A에서 작성한 이름이 B에 제출되는 것을 확인했습니다. 입력 상태를 대상별로 구분하고 미저장 이동을 확인하겠습니다. 저장 실패 후 복구와 검색 역순 응답도 각각 재현 테스트로 확인하겠습니다.”

## 10. 코드를 받는 사전 1시간에 할 일

사전 수정·실행·검색의 허용 범위는 전달받은 안내를 따릅니다. 아래는 읽기와 메모 중심 배분이며, 읽기만 허용되면 재현할 시나리오를 적고 실행은 면접 중에 합니다.

| 시간 | 행동 | 남길 결과 |
| --- | --- | --- |
| 0~10분 | README·scripts·화면 진입점·요구사항 확인 | 실행 명령, 주요 기능, 모르는 계약 |
| 10~25분 | 핵심 사용자 동작 하나를 UI→핸들러→API→state→UI로 추적 | 입력·출력·변경 대상의 흐름 |
| 25~40분 | 실패·연속 동작·항목 변경·빈 입력을 확인 또는 계획 | 기대/실제, 재현 순서 |
| 40~50분 | 확정 결함과 의심을 나누고 우선순위 결정 | 먼저 고칠 2~3개와 근거 |
| 50~60분 | 최소 수정과 테스트 계획, 전체 설명 정리 | 첫 설명에 사용할 메모 |

모든 파일을 같은 깊이로 읽지 않습니다. 스타일 파일보다 실제 사용자 행동이 값을 바꾸는 경로부터 추적합니다. 그렇다고 UI를 무작위로 클릭하지도 않습니다. “선택 변경 시 초안이 어떻게 되는지 확인하겠다”처럼 시나리오를 세웁니다.

```text
기능: 검색 / 선택 / 편집 / 저장
입력과 출력:
원본 상태와 파생값:
변경 요청의 대상:
확인된 결함: 재현 조건 → 기대 → 실제
아직 가설인 부분:
우선순위와 사용자 영향:
최소 수정과 대안:
검증할 성공 / 실패 / 재시도 / 연속 동작:
확인할 요구사항:
```

모호한 요구사항은 구현 취향 대신 제품 동작으로 묻습니다. “B로 이동할 때 A의 미저장 입력은 폐기하나요, 보관하나요?”, “조회 실패 시 이전 결과를 유지하나요?”처럼 답에 따라 수정이 달라지는 질문을 고릅니다.

## 11. 실제 수정 시간에는 이렇게 진행하기

**재현 → 실패 테스트 → 최소 수정 → 같은 테스트 통과 → 인접 경로 확인**을 한 문제씩 반복합니다. 테스트의 import 오류나 잘못된 선택자 때문에 실패한 것은 제품 결함의 재현이 아닙니다.

| 우선 검토할 영향 | 예시 |
| --- | --- |
| 잘못된 대상 변경·데이터 손실 | 다른 항목에 저장, 입력 소실 |
| 성공 오인·복구 막힘 | 서버 거절인데 완료 표시, 버튼 영구 잠금 |
| 잘못된 표시·탐색 | 오래된 검색 결과, 잘못된 합계 |
| 유지보수·성능 | 모순된 정책, 측정된 입력 지연 |
| 형식 | 관련 없는 이름·간격 정리 |

절대 순위표는 아닙니다. 화면이 완전히 멈추는 성능 문제는 먼저 처리해야 할 수 있습니다. 영향·재현·복구 가능성·선행 관계·남은 시간으로 판단합니다.

수정 전후에는 사용자가 보는 값, 오류, 버튼, 요청 대상을 확인합니다. 내부 state 이름이나 함수 분리 형태를 테스트 정답으로 고정하지 않습니다.

이 저장소에서는 관련 테스트 이후 `pnpm typecheck`, `pnpm lint` 등을 사용합니다. 낯선 저장소에서는 package.json의 실제 명령을 먼저 확인합니다. 실행한 검사와 실행하지 못한 검사를 나누어 말합니다. 모의 API 테스트가 통과했다고 실제 서버 권한·중복 방지까지 검증된 것은 아닙니다.

## 12. 예상 꼬리질문 — 답의 방향까지 익히기

| 질문 | 답변에 담을 핵심 |
| --- | --- |
| 왜 이걸 먼저 고쳤나요? | 사용자 영향, 재현 증거, 복구 어려움과 선행 관계 |
| 왜 state를 없앴나요? | 원본에서 계산 가능해 동기화 대상이 불필요했음; 초안은 예외 |
| 왜 Effect를 없앴나요? | 외부 동기화가 아닌 표시 계산이었음; Effect 자체를 금지한 것이 아님 |
| 왜 훅으로 분리했나요? | 함께 바뀌는 상태 수명주기를 모았음; 순수 계산은 함수로 충분 |
| 더 공통화하지 않나요? | 모양보다 변경 이유를 봄; 예외 옵션과 불필요한 결합 비용 |
| debounce면 해결되지 않나요? | 요청 빈도와 응답 소속은 별개 |
| 버튼 disabled면 중복 방지가 끝인가요? | UI 경로를 줄일 뿐 다른 호출 경로와 서버 재시도 계약은 별도 |
| TypeScript가 있는데 왜 검증하나요? | 입력 문자열과 외부 응답의 런타임 내용은 정적 타입만으로 보장되지 않음 |
| 테스트 하나 통과했으면 충분한가요? | 재현 결함은 확인했지만 실패 후 재시도와 관련 정상 경로도 봐야 함 |

말하기는 다음 네 문장으로 시작하면 됩니다.

> “이 코드는 [입력]을 받아 [동작] 후 [결과]를 보여줍니다.”
>
> “[재현 조건]에서 [기대]와 달리 [실제]가 나타납니다.”
>
> “원인이 [구체적 흐름]이므로 [최소 변경]을 선택했습니다. [대안]은 [비용·조건] 때문에 지금은 선택하지 않았습니다.”
>
> “[검증 결과]를 확인했고 [미확인 범위]는 남아 있습니다.”

마지막으로 낯선 코드에서 **값의 원본, 값의 소속, 요청의 순서, 실패 후 상태, 변경 책임**을 찾으세요. 이 다섯 가지를 재현 가능한 설명으로 연결하는 것이 이 속성 과정의 목표입니다.
