# 00. 코드를 어디서부터 읽을까

목표는 모든 문법을 외우는 것이 아니라, 한 번의 사용자 행동이 어떤 결과를 만드는지 따라가는 것입니다.

## 먼저 알아둘 말

| 용어      | 뜻                                            | 예                                    |
| --------- | --------------------------------------------- | ------------------------------------- |
| 입력      | 함수나 화면이 받는 값                         | 검색어, API 응답, props               |
| 출력      | 만들어 반환하거나 표시하는 값                 | 필터된 목록, 합계                     |
| props     | 부모가 자식에게 전달한 입력                   | `<List items={items} />`              |
| state     | React가 다음 렌더에도 기억하는 값             | 사용자가 입력 중인 검색어             |
| 렌더      | 현재 입력과 state로 화면 설명을 계산하는 과정 | 컴포넌트 함수 실행                    |
| 이벤트    | 클릭·입력처럼 발생한 행동                     | `onClick`, `onChange`                 |
| 부수 효과 | 계산 밖의 시스템에 영향을 주는 일             | 요청, 타이머, 구독                    |
| 불변식    | 어느 경로에서도 지켜야 하는 조건              | 저장 실패로 확정 데이터가 바뀌지 않음 |
| 회귀      | 고친 뒤 예전에 되던 동작이 깨짐               | 오류 처리를 고쳤는데 재시도가 안 됨   |
| 경쟁 상태 | 처리 순서에 따라 결과가 달라지는 상황         | 늦은 응답이 최신 검색을 덮음          |

## 짧은 코드 따라가기

```tsx
import { useState } from 'react';

type Book = { id: string; title: string };

export function Books({ books }: { books: Book[] }) {
  const [keyword, setKeyword] = useState('');
  const visible = books.filter((book) => book.title.includes(keyword));
  return (
    <section>
      <label>
        책 검색
        <input value={keyword} onChange={(event) => setKeyword(event.target.value)} />
      </label>
      <p>{visible.length}권</p>
      {visible.map((book) => (
        <p key={book.id}>{book.title}</p>
      ))}
    </section>
  );
}
```

`Book`은 객체의 모양을 설명하는 타입입니다. `books`는 부모가 제공한 목록이고 `keyword`는 이 화면이 소유하는 입력 상태입니다. `filter`는 조건에 맞는 항목으로 새 배열을 만들며, `map`은 각 항목을 화면 요소로 바꿉니다.

이 코드는 “키워드 입력 → 상태 변경 예약 → 다시 렌더 → 필터 계산 → 화면 반영”으로 읽습니다. `visible`을 바꾸는 별도 버튼이나 Effect는 필요하지 않습니다. 입력과 원본 목록만 알면 결과를 계산할 수 있기 때문입니다.

## 코드보다 먼저 요구사항 확인하기

검색어가 공백이면 전체 목록인가, 공백도 검색하는가? 대소문자는 구분하는가? 이 코드만으로 제품의 의도를 결정할 수 없습니다. 예를 들어 현재 코드는 제목에 공백이 포함되어야 공백 검색에 잡힙니다. 그것이 결함인지 판단하려면 요구사항이 필요합니다.

좋은 확인 문장: “검색어 앞뒤 공백은 제거하고 대소문자는 무시하는 것이 기대 동작인가요?”

나쁜 단정: “trim이 없으니까 무조건 버그입니다.”

## 전체 프로젝트 읽는 순서

1. 화면의 진입 컴포넌트에서 입력과 출력을 찾습니다.
2. 이벤트가 호출하는 함수와 Hook을 따라갑니다.
3. API의 성공·실패 계약과 응답 타입을 확인합니다.
4. 상태를 누가 소유하며 어떤 사건이 변경하는지 적습니다.
5. 요구사항 하나를 구체적인 입력과 조작으로 바꿉니다.

파일을 순서 없이 모두 읽는 것보다 “저장 버튼을 누르면 어떤 값이 어디로 전달되는가” 하나를 끝까지 따라가는 편이 흐름을 파악하기 쉽습니다.

## 변형 질문과 해설

**질문:** 부모가 새 책 목록을 주면 검색 결과도 갱신되는가?

**해설:** 새 props로 렌더할 때 `filter`를 다시 실행하므로 갱신됩니다. 결과를 초기 state에만 복사해 두었다면 새 props를 반영하는 별도 정책이 필요했을 것입니다.

**설명 예시:** “검색어는 사용자 행동으로 변하는 원본 상태이고, 목록과 검색어로 결정되는 검색 결과는 렌더 때 계산합니다.”
