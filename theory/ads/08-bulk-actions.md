# 08. 일괄 중지의 일부 성공과 실패를 구분하지 못한다

## 개념부터 풀어보기

이 수업의 일괄 중지는 하나의 큰 트랜잭션이 아니라 광고마다 독립적인 중지 요청을 보내는 작업입니다. A가 성공해도 B는 실패할 수 있습니다. ‘원자적 일괄 작업’은 모두 적용되거나 아무것도 적용되지 않는 별도 서버 보장을 뜻합니다.

`Promise.all`은 하나가 reject하면 전체 대기를 reject하지만 이미 시작한 나머지 요청을 취소하지 않습니다. 제시된 Before도 B가 reject하면 성공 토스트까지 실행되지는 않습니다. 핵심 결함은 이 코드에 개별 결과를 수집하고 보여주는 흐름이 없다는 점입니다. API가 업무상 거절을 fulfilled로 반환하는데 검사하지 않는 경우에는 잘못된 전체 성공 표시까지 생길 수 있습니다.


## 요구사항과 Before

같은 계정의 광고 A·B·C를 중지합니다. 각각 독립적인 서버 작업입니다. A·C는 중지되고 B는 명시적으로 거절될 수 있습니다. 성공한 대상은 재시도하지 않습니다.

```ts
await Promise.all(selectedIds.map((id) => api.pause(id)));
setSelectedIds([]);
showToast('모두 중지했습니다.');
```

## 재현과 우선순위

B만 거절시키면 Promise.all이 reject하지만 A·C 작업은 자동으로 취소되지 않습니다. catch에서 “모두 실패”라고 표시하고 전체 재시도해도 사실과 다릅니다. 중지를 요청한 광고가 계속 운영될 수 있어 결과를 정확히 알리는 일을 우선합니다.

## After

```ts
const ids = [...selectedIds]; // 클릭 시 작업 대상을 고정
const results = await Promise.allSettled(ids.map((id) => api.pause(id)));
const outcomes = results.map((result, index) => ({
  id: ids[index],
  state:
    result.status === 'fulfilled'
      ? 'success'
      : isExplicitRejection(result.reason)
        ? 'rejected'
        : 'unknown',
}));
```

API가 HTTP 비정상 응답을 throw하고 성공 응답을 확인한다는 계약입니다. fetch는 HTTP 500만으로 Promise를 reject하지 않으므로 API 계층이 상태를 검사해야 합니다. `allSettled`는 결과를 모을 뿐 동시 요청 수를 제한하지 않습니다.

결과 UI에는 성공 2건, 거절 1건처럼 사실을 표시합니다. 네트워크 끊김은 서버에서 성공했는지 모를 수 있으므로 결과 불명으로 두고 재조회합니다. 실패 항목 재시도도 작업이 멱등적인지 확인해야 합니다. “중지 상태로 설정”과 “현재 상태 반전”은 재시도의 효과가 다릅니다.

## 세 가지 결과를 구분하기

| 결과 | 확인된 사실 | 후속 동작 |
| --- | --- | --- |
| success | 서버가 중지 성공을 확인함 | 성공 표시, 재시도 대상에서 제외 |
| rejected | 서버가 적용하지 않았음을 명시적으로 확인함 | 이유 표시, 원인 해결 뒤 재시도 검토 |
| unknown | 서버 적용 여부를 확인하지 못함 | 상태나 작업 이력 재조회 |

모든 HTTP 오류를 rejected로 분류하면 안 됩니다. 서버 내부 오류가 변경 전 발생했는지 변경 후 발생했는지 모를 수 있습니다. `isExplicitRejection`은 ‘미적용이 보장되는 오류’라는 API 계약을 기준으로 구현해야 합니다. 네트워크 단절과 타임아웃은 보통 적용 여부를 확정할 수 없습니다.

## After의 실행 순서

1. `[...selectedIds]`로 클릭 시점의 대상 목록을 복사합니다.
2. 각 대상에 중지 요청을 보냅니다.
3. `allSettled`로 성공·실패가 모두 끝날 때까지 기다립니다.
4. 결과는 완료 순서가 아니라 입력 순서로 반환되므로 `ids[index]`로 원래 대상과 연결합니다.
5. UI에는 결과별 개수와 항목별 이유를 보여주고 성공한 항목을 재시도 대상에서 뺍니다.

실제 구현은 ID뿐 아니라 accountId도 제출 시점에 고정해야 합니다. 작업 중 선택 변경을 허용한다면 새로 선택한 행까지 완료 콜백에서 지우지 않도록 선택 상태 갱신 정책도 필요합니다.

‘멱등적’이라는 말은 같은 요청을 반복해도 의도한 최종 상태가 중복으로 변하지 않는다는 뜻입니다. ‘PAUSED로 설정’은 반복해도 PAUSED지만 ‘현재 상태 반전’은 두 번 실행하면 원상태가 될 수 있습니다. 로그·알림 같은 부수 효과의 중복까지 방지되는지는 별도 계약입니다.

allSettled는 동시 실행 개수를 제한하지 않습니다. 1,000개 ID에 바로 map하면 1,000개 요청을 시작할 수 있습니다. 요청 제한이나 서버 bulk API가 필요한지는 규모와 서버 계약으로 판단합니다. 끝나지 않는 요청이 있으면 전체 결과도 늦어지므로 타임아웃과 진행 상태도 정의해야 합니다.

## 검증

일부 성공·전부 성공·명시적 거절·결과 불명을 나눕니다. 작업 시작 후 선택이 바뀌어도 ID와 결과 매칭이 유지돼야 합니다. 성공한 항목은 실패 재시도에 포함하지 않습니다. 수천 개 대상은 서버 bulk API 또는 동시 실행 제한을 고려합니다.

## 면접에서 말하기

> “일괄 작업은 부분 성공이 가능합니다. 제출 대상 ID를 고정하고 개별 결과를 수집하겠습니다. 타임아웃은 확정 실패와 구분해 재조회하고, 성공한 대상까지 무조건 재시도하지 않겠습니다.”

**꼬리질문:** allSettled로 바꾸면 일괄 작업이 원자적이 되는가?

**해설:** 아닙니다. 전체 성공 또는 전체 취소가 필요하면 서버 트랜잭션이나 별도 작업 계약이 필요합니다. 프론트 Promise 조합으로 되돌림을 보장할 수 없습니다.
