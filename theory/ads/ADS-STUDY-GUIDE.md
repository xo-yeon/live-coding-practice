가상의 운영자는 광고 계정을 고르고, 캠페인 목록에서 성과를 확인한 뒤, 예산을 수정하거나 광고를 시작·중지합니다. 필요하면 기간별 보고서를 내려받습니다. 12개 장은 이 흐름에서 데이터가 잘못 표시되거나 다른 대상에 저장되는 상황을 각각 설명합니다.

캠페인은 광고를 관리하는 단위이고 소재는 사용자에게 보여줄 이미지·문구 같은 광고 콘텐츠입니다. 이 교재에서는 개념을 익히기 위한 최소 관계만 사용합니다. 실제 서비스마다 캠페인·그룹·소재의 계층과 정책은 다를 수 있습니다.

## 문서와 코드를 읽는 방법

각 장은 개념 설명, 요구사항과 Before, 재현과 사용자 영향, After와 상세 해설, 검증, 면접 답변 순서로 읽습니다. Before는 왜 문제가 생기는지 관찰할 코드이고 After는 특정 전제에서 이를 개선하는 코드입니다. 면접 답변은 이해한 뒤 설명을 정리하는 예시이며 외울 정답 문장이 아닙니다.

코드의 `api`, `Campaign`, `Props`, 상태 setter, 오류 판별 함수는 주변 앱이 제공한다고 가정합니다. `api`는 이 저장소 전체에서 하나의 확정된 SDK를 뜻하지 않습니다. 장별로 입력과 실패 계약을 설명하기 위한 이름입니다. 코드 블록 전체를 한 파일에 붙여 실행하는 방식으로 설계한 자료는 아닙니다.

예를 들어 `isConflict`는 409 충돌을 판별하고, `isExplicitRejection`은 서버가 변경 미적용을 보장한 오류를 판별합니다. 두 함수를 단순히 ‘오류가 있으면 true’로 구현하면 설명한 구분이 사라집니다. 단위 함수 테스트가 통과해도 계정 권한·DB 저장 원자성·실제 UI까지 검증된 것은 아닙니다.

## 01. 카드 광고 대시보드의 전체 CTR이 틀린다

### 개념부터 풀어보기

CTR(클릭률)은 노출 중 클릭이 발생한 비중이고, CPC(클릭당 비용)는 광고비를 클릭 수로 나눈 값입니다. `impressions`는 노출 수, `clicks`는 클릭 수, `spendWon`은 원 단위 광고비입니다. 노출 1,000회·클릭 10회·비용 5,000원이면 CTR은 1%, CPC는 500원입니다.

‘광고별 CTR의 평균’과 ‘전체 노출 중 클릭 비중’은 서로 다른 질문입니다. 아래 예시에서 A는 노출 10회, B는 990회인데 단순 평균을 내면 두 광고의 영향력이 같아집니다. 전체 CTR에는 노출 규모가 반영되어야 합니다.

### 요구사항과 Before

가상 카드 광고 A·B의 같은 기간·같은 통화·같은 집계 기준 데이터를 합쳐 표시합니다. CTR은 클릭/노출 × 100, CPC는 비용/클릭입니다. 분모가 0이면 계산 불가를 `—`로 표시합니다. 원 단위 비용은 합산하고, 반올림은 표시할 때만 합니다.

```ts
const ctr = (rows.reduce((sum, row) => sum + row.clicks / row.impressions, 0) / rows.length) * 100;
```

### 재현과 우선순위

A는 10회 노출·1회 클릭(10%), B는 990회 노출·9회 클릭(약 0.91%)입니다. 단순 평균은 약 5.45%지만 전체는 10/1,000 = 1%입니다.

성과를 비교해 예산을 옮기는 화면이라면 잘못된 지표는 운영 판단에 영향을 줍니다. 표시 간격 같은 스타일보다 먼저 고칩니다. 다만 현재 다른 광고 계정에 잘못 저장하는 문제가 있다면 그 변경 경로부터 막는 것이 우선일 수 있습니다.

### After와 근거

```ts
const total = rows.reduce(
  (sum, row) => ({
    impressions: sum.impressions + row.impressions,
    clicks: sum.clicks + row.clicks,
    spendWon: sum.spendWon + row.spendWon,
  }),
  { impressions: 0, clicks: 0, spendWon: 0 },
);

const ctrPercent = total.impressions === 0 ? null : (total.clicks / total.impressions) * 100;
const cpcWon = total.clicks === 0 ? null : total.spendWon / total.clicks;
```

비율은 분자와 분모를 각각 합산한 뒤 다시 계산합니다. 평균값의 평균을 구하지 않습니다. `null`은 0%와 다릅니다. 노출 100·클릭 0은 CTR 0%이고 노출 0은 계산 불가입니다. CPC를 계산할 수 없다고 0원으로 보여주면 무료 클릭인 것처럼 오인할 수 있습니다.

이 함수는 유효한 비음수 데이터가 들어온다는 전제입니다. API 경계에서 NaN·음수·통화 혼합을 검증해야 합니다. 카드 신청 전환 수를 매출액으로 취급해 ROAS를 계산하지 않습니다. 전환 정의·귀속 기간·분모를 먼저 확인합니다.

### After 코드가 보장하는 것

1. `reduce`는 각 행의 노출·클릭·비용을 각각 더합니다. 초기값이 모두 0이므로 빈 배열도 계산할 수 있습니다.
2. 합산이 끝난 뒤 CTR·CPC를 구합니다. 이미 계산된 비율을 더하는 것이 아닙니다.
3. 분모가 0이면 `null`을 반환합니다. UI에서 `—`와 계산 불가 이유를 보여줄 수 있습니다.
4. 표시할 때만 반올림합니다. 행별 반올림 후 합산하면 중간 오차가 누적될 수 있습니다.

| 입력 | 기대 결과 | 이유 |
| --- | --- | --- |
| 노출 100, 클릭 0 | CTR 0%, CPC 계산 불가 | 노출은 있었지만 클릭당 비용을 계산할 클릭이 없음 |
| 노출 0, 클릭 0 | CTR·CPC 계산 불가 | 두 지표 모두 분모가 0 |
| 비용 100원, 클릭 3회 | 원본 CPC 100/3 | 정수 원 표시는 별도의 반올림 정책 |
| 성공적으로 조회한 빈 목록 | 합계 0, 비율 계산 불가 | 조회 실패를 빈 목록으로 바꿔 넣어서는 안 됨 |

‘같은 집계 기준’은 기간·시간대·대상 범위가 일치하고 중복 집계가 없다는 뜻입니다. 오늘 A 성과와 이번 달 B 성과를 합쳐 오늘의 성과라고 표시하면 안 됩니다. `NaN`은 숫자 계산이 성립하지 않았음을 나타내는 특수값이며 그대로 화면에 노출하지 않도록 입력을 검증합니다.

ROAS는 광고비 대비 매출액 비율입니다. 신청 건수는 매출 금액이 아닙니다. ‘전환’이 신청인지 승인인지, 광고 이후 며칠까지 발생한 행동을 성과로 인정하는지(귀속 기간)를 확인해야 서로 비교할 수 있습니다.

### 검증

- 위 A·B 데이터에서 CTR 1%인지 확인합니다.
- 클릭 0일 때 CPC가 null이고, UI가 `—`를 표시하는지 확인합니다.
- 비용 100원·클릭 3회의 원본 CPC는 100/3을 유지하고 표시만 반올림합니다.
- 요약이 전체 필터 결과인지 현재 페이지만인지 확인합니다.

### 면접에서 말하기

> “행별 CTR 평균은 노출 규모 차이를 반영하지 못합니다. 전체 클릭과 노출을 합산해 다시 계산하겠습니다. 운영자의 예산 판단에 영향을 주므로 표현 개선보다 우선하고, 0%와 계산 불가도 구분하겠습니다.”

**꼬리질문:** 필터 결과가 100개인데 20개만 받았다면?

**해설:** 20개로 계산한 값을 전체 합계로 표시하면 안 됩니다. 서버 요약을 받거나 전체 데이터를 확보해야 합니다. 지금 계산의 범위를 라벨에 명시하는 것도 중요합니다.

## 02. 성과가 없는 캠페인이 목록에서 사라진다

### 개념부터 풀어보기

캠페인 메타데이터는 ID·이름·운영 상태처럼 ‘어떤 광고인가’를 설명합니다. 성과는 노출·클릭·비용처럼 ‘얼마나 집행되었는가’를 설명합니다. 새 캠페인은 이름과 ID가 있어도 아직 성과가 없을 수 있습니다.

이 화면의 목적은 캠페인 관리입니다. 따라서 목록에 나올 대상은 캠페인 API가 결정하고 성과는 나중에 붙입니다. 이것을 ‘캠페인을 기준으로 결합한다’고 표현합니다.

### 요구사항과 Before

가상 대출 광고 운영 화면에는 오늘 생성한 캠페인도 보여야 합니다. 캠페인 목록과 성과 API는 별개이며 이 수업에서 성과 행 누락은 **미집계**를 뜻합니다. 행이 존재하고 노출이 0인 경우만 확정된 0으로 표시합니다.

```ts
const rows = metrics.map((metric) => ({
  ...campaigns.find((campaign) => campaign.id === metric.campaignId),
  ...metric,
}));
```

### 재현과 우선순위

캠페인은 A·B 두 개이고 성과 응답에는 A만 넣습니다. B가 화면에서 사라져 생성 실패로 오해할 수 있습니다. 신규 캠페인 확인이 핵심 운영 흐름이라면 먼저 고칠 동작 문제입니다.

### After

```ts
const byId = new Map(metrics.map((metric) => [metric.campaignId, metric]));
const rows = campaigns.map((campaign) => ({
  ...campaign,
  metric: byId.get(campaign.id) ?? null,
}));
```

목록의 기준은 캠페인 원본이고 성과는 부가 정보입니다. 메타데이터를 유지하면서 성과만 없다고 표현합니다. `null`을 임의로 0으로 바꾸지 않습니다. 다른 API에서 누락을 0으로 보장한다면 그 계약에 한해서 0을 채울 수 있습니다.

조회 실패·아직 로딩·성공했지만 행 없음도 구분합니다. 모든 누락을 `?? 0`으로 처리하면 장애까지 정상적인 0 실적으로 표시할 수 있습니다. 유일 ID를 보장하지 않는 응답이면 Map 생성 전에 중복 정책도 필요합니다.

### Before와 After를 따라가기

Before의 `metrics.map`은 성과가 있는 행만 순회합니다. 성과에 B가 없으면 B를 만들 기회 자체가 없습니다. After는 `campaigns.map`으로 A·B를 모두 만들고, Map에서 해당 성과를 찾습니다. Map은 `캠페인 ID → 성과 객체`를 저장하는 조회표입니다.

성과를 `metric` 필드 안에 넣으면 캠페인과 성과에 같은 이름의 필드가 있어도 서로 덮어쓰지 않습니다. `?? null`은 찾은 성과가 없을 때만 null을 채웁니다.

| 상태 | 의미 | 화면 |
| --- | --- | --- |
| 조회 중 | 응답이 아직 없음 | 성과 영역 로딩 |
| 성공, 행 있음, 값 0 | 서버가 0으로 집계함 | 0 |
| 성공, 해당 행 없음 | 이 수업의 계약상 미집계 | 미집계 |
| 조회 실패 | 성과를 알 수 없음 | 오류와 재시도 |

위 결합 함수는 **성과 API가 성공한 다음의 변환**입니다. 로딩·실패까지 null로 바꾸는 함수가 아닙니다. 조회 상태를 별도로 관리해야 장애를 ‘실적 없음’으로 오해하지 않습니다.

같은 ID가 여러 번 들어오면 Map은 나중 값을 남깁니다. 일별 성과 여러 행이라면 합산이 필요할 수 있고, 잘못된 중복이면 오류로 다뤄야 합니다. ‘ID가 유일하다’는 전제가 없는 곳에 그대로 적용하지 않습니다.

작은 목록을 클라이언트에서 합치는 것은 합리적일 수 있습니다. 그러나 캠페인 100개 중 20개와 성과 100개 중 다른 20개만 가져왔다면 두 응답을 합쳐도 전체 목록은 되지 않습니다. 서버 결합 여부보다 먼저 조회 범위를 확인합니다.

### 검증

A만 성과가 있는 상황에서도 A·B 두 행이 보여야 합니다. A의 노출 0은 `0`, B는 `미집계`로 표현합니다. 성과 API 실패 시 캠페인 목록은 유지하고 성과 영역에 오류·재시도를 표시하는 것이 이 수업의 정책입니다.

### 면접에서 말하기

> “성과 응답을 목록의 기준으로 사용해 미집계 캠페인이 빠집니다. 캠페인 목록을 기준으로 결합하고, 조회 실패와 미집계를 0과 구분하겠습니다.”

**꼬리질문:** 프론트에서 목록을 합치면 항상 좋은가?

**해설:** 데이터 상한, 응답 크기, 서버 조인 지원 여부에 따라 다릅니다. 여러 페이지 중 일부만 받아 합치면 완전한 목록이 되지 않습니다. 계약을 확인한 작은 수정과 전체 조회 구조 변경을 구분해야 합니다.

## 03. 두 운영자가 수정한 예산이 서로 덮인다

### 개념부터 풀어보기

**초안**은 사용자가 입력 중인 값이고 **확정값**은 서버가 저장했다고 확인한 값입니다. 저장 버튼을 눌렀다는 사실만으로 확정값을 바꾸지 않는 것이 이 수업의 정책입니다. 서버 응답 전에 화면부터 바꾸는 방식을 낙관적 업데이트라고 부르며, 사용하려면 실패 복구와 동시 변경 처리가 추가로 필요합니다.

`expectedVersion: 7`은 ‘나는 버전 7을 보고 수정했으니, 서버도 아직 7일 때만 저장해 달라’는 조건입니다. 이 조건을 이용해 동시 편집 충돌을 감지하는 방식을 낙관적 동시성 제어라고 합니다. 낙관적 **화면 업데이트**와는 다른 개념입니다.

### 요구사항과 Before

가상 캠페인의 일 예산은 10,000~10,000,000원 정수입니다. 응답에는 `version`이 있으며 서버는 오래된 version의 수정을 409로 거절합니다. 실패 시 초안을 유지하고 확정값은 바꾸지 않습니다.

```ts
setCampaign({ ...campaign, dailyBudget: Number(raw) });
await api.updateBudget(campaign.id, { dailyBudget: Number(raw) });
```

### 재현과 우선순위

나와 동료가 version 7을 엽니다. 동료가 20만원으로 바꿔 version 8이 됩니다. 내가 오래된 화면에서 15만원을 제출합니다. 버전을 요구하는 서버라면 이 요청을 거절해야 합니다. 조건 없는 저장을 허용한다면 동료 변경을 덮을 수 있습니다. 잘못된 집행 조건 변경이나 저장 실패를 성공처럼 보여주는 문제는 가독성 리팩터링보다 우선합니다. 실제 추가 과금 발생 여부까지 확인 없이 단정하지 않습니다.

### After: 제출한 값을 고정하고 충돌 구분

아래는 저장 핸들러의 발췌입니다. `parseBudget`은 위 금액 계약을 검사하고 `api.updateBudget`은 비정상 HTTP 상태를 분류하여 throw한다고 가정합니다.

```ts
const command = {
  accountId,
  campaignId: campaign.id,
  dailyBudget: parseBudget(raw),
  expectedVersion: campaign.version,
};
try {
  const saved = await api.updateBudget(command);
  setCampaign(saved);
  setRaw(String(saved.dailyBudget));
} catch (error) {
  if (isConflict(error)) {
    setError('다른 변경이 있습니다. 최신 예산을 확인한 후 다시 저장해주세요.');
  } else {
    setError('저장에 실패했습니다. 입력값은 유지됩니다.');
  }
}
```

계정·ID·금액·version을 제출 시점 값으로 묶습니다. 수정 성공에 사용한 command의 계정/ID에 해당하는 캐시만 갱신합니다. 저장 중 계정·항목 변경을 막거나 편집기를 분리하는 정책도 필요합니다.

409에서 최신 version으로 바꿔 자동 재시도하면 충돌 보호를 무력화할 수 있습니다. 최신 상태를 보여주고 사용자가 자신의 의도를 다시 확인하게 합니다. version은 프론트에서 비교만 하는 값이 아니라 서버가 저장과 함께 원자적으로 검사해야 합니다.

### 버전 충돌을 시간 순서로 이해하기

| 순서 | 내 화면 | 서버 |
| --- | --- | --- |
| 1 | 버전 7 조회 | 버전 7 |
| 2 | 15만원 입력 중 | 동료가 20만원 저장, 버전 8 |
| 3 | 15만원과 expectedVersion 7 제출 | 현재 8과 달라 409 거절 |
| 4 | 내 초안 15만원 유지, 충돌 안내 | 동료의 20만원 유지 |

서버가 버전 누락 요청도 거절한다면 Before는 덮어쓰기 대신 저장 실패를 일으킵니다. **버전을 보내지 않았다는 사실만으로 실제 덮어쓰기가 발생했다고 단정하지 않습니다.** 서버가 조건 없는 저장을 허용할 때 덮어쓰기 위험이 생깁니다.

‘원자적 검사’는 버전 확인과 저장 사이에 다른 변경이 끼어들 수 없도록 하나의 조건부 변경으로 처리한다는 뜻입니다. 서버에서 먼저 조회하고 나중에 별도로 저장하면 그 사이 값이 바뀔 수 있습니다. 프론트에서 버전을 비교하는 것만으로는 이를 막을 수 없습니다.

### 코드의 생략된 전제와 복구 흐름

`command`는 제출 당시 계정·광고·금액·버전을 묶은 변경 요청입니다. `await` 이후 현재 선택 항목이 바뀌었더라도 이 요청이 속한 대상은 변하지 않습니다. 아래 핸들러는 저장 중 항목 이동과 추가 입력을 막는 편집기를 전제로 읽으세요. 이동을 허용한다면 응답을 command 대상의 캐시에만 적용해야 합니다.

`parseBudget`은 문자열을 숫자로 바꾸기 전에 원 단위 정수와 범위를 검사합니다. 빈 문자열을 바로 `Number`에 넣으면 0이 되므로 단순 변환만으로 유효성을 판정하지 않습니다. 검증 오류도 사용자에게 보여줘야 하며, 아래 발췌처럼 try 밖에서 호출한다면 별도의 폼 검증 처리가 필요합니다.

409에서 버전만 8로 바꿔 15만원을 자동 재전송하면 동료의 20만원을 결국 덮습니다. 최신값과 내 초안을 함께 보여주고 사용자가 재저장 의도를 확인하도록 합니다. 최신값을 확인해도 초안을 자동으로 지우지 않습니다.

타임아웃은 ‘응답을 제시간에 받지 못함’입니다. 서버가 저장을 완료했을 수도 있습니다. 재조회나 작업 ID로 결과를 확인하고, 동일 요청을 여러 번 보내도 효과가 중복되지 않는다는 서버 계약(멱등성)이 있을 때 그 계약에 따라 재시도합니다.

### 검증

정상 저장, 범위 오류, 저장 거절, 409 각각을 검사합니다. version 8 상태에 version 7 명령은 거절되어야 합니다. 409 후 초안은 유지되고 자동 재요청되지 않아야 합니다. 저장 중 중복 진입은 앞선 공통 이론의 잠금 방식을 사용합니다.

### 면접에서 말하기

> “예산 변경은 서버 확정 전 반영하지 않겠습니다. 여러 운영자의 편집을 고려해 읽은 version을 함께 보내고, 충돌은 일반 통신 실패와 구분하겠습니다. 서버의 원자적 검사 없이 프론트만으로 덮어쓰기를 막을 수는 없습니다.”

**꼬리질문:** 요청이 타임아웃이면 저장 실패인가?

**해설:** 결과를 모르는 상태일 수 있습니다. 서버에서 이미 저장됐을 수도 있으므로 재조회하거나 작업 식별자로 확인합니다. 재전송 정책은 멱등성 계약과 함께 정합니다.

## 04. 심사 중인 광고가 운영중으로 바뀐다

### 개념부터 풀어보기

심사 상태는 ‘광고 내용이 승인되었는가’, 운영 상태는 ‘광고를 현재 집행하는가’를 나타냅니다. 승인된 광고도 운영자가 중지해 둘 수 있으므로 두 상태를 하나의 값으로 취급하지 않습니다.

| 심사 | 운영 | 편집 권한 | 시작 가능 여부 |
| --- | --- | --- | --- |
| APPROVED | PAUSED | 있음 | 가능 |
| PENDING 또는 REJECTED | PAUSED | 있음 | 불가: 승인 필요 |
| APPROVED | ENDED | 있음 | 불가: 종료됨 |
| APPROVED | ACTIVE | 있음 | 불가: 이미 운영 중 |
| APPROVED | PAUSED | 없음 | 불가: 권한 없음 |

Before는 ACTIVE가 아니면 전부 ACTIVE로 바꿉니다. 그래서 PAUSED뿐 아니라 ENDED도 시작 대상으로 취급합니다. ‘현재 값의 반대’만 계산해서는 시작 가능한 조건을 표현할 수 없습니다.

### 학습용 요구사항과 Before

심사 상태는 PENDING·APPROVED·REJECTED이고 운영 상태는 PAUSED·ACTIVE·ENDED입니다. 편집 권한이 있고 심사가 승인되었으며 종료되지 않은 광고만 시작할 수 있습니다. 이는 가상 정책입니다.

```ts
const nextStatus = campaign.status === 'ACTIVE' ? 'PAUSED' : 'ACTIVE';
await api.setStatus(campaign.id, nextStatus);
```

### 재현과 우선순위

심사 PENDING, 운영 PAUSED를 넣고 토글합니다. UI가 시작 요청을 보내면 정책과 다른 동작입니다. 서버가 거절해도 불필요한 요청과 잘못된 기대를 만듭니다. 서버까지 허용한다면 실제 집행 위험이 있으므로 변경 경로의 안전성을 먼저 확인합니다.

### After

```ts
function canActivate(campaign: Campaign, canEdit: boolean) {
  if (!canEdit) return { allowed: false, reason: '편집 권한 없음' };
  if (campaign.status === 'ENDED') return { allowed: false, reason: '종료된 광고' };
  if (campaign.status === 'ACTIVE') return { allowed: false, reason: '이미 운영중' };
  if (campaign.review !== 'APPROVED') return { allowed: false, reason: '심사 승인 필요' };
  return { allowed: true, reason: '' };
}
```

버튼 disabled와 안내문에 같은 결정 결과를 사용합니다. 시작·중지·종료는 다른 명령입니다. 가능한 상태가 늘어날 때 무조건 반대로 뒤집는 boolean 토글을 피합니다. 서버에서 갱신된 정식 상태를 받아 표시합니다.

이 함수는 UI 정책이며 보안 경계가 아닙니다. 서버도 권한·심사·현재 상태를 검사합니다. 응답 대기 중 다른 운영자가 상태를 바꿀 수 있으므로 서버 거절을 정상적인 복구 경로로 다룹니다.

### 정책 함수를 실제 화면에 연결하기

`canActivate`는 서버를 호출하거나 상태를 바꾸는 함수가 아닙니다. 입력을 보고 `allowed`와 `reason`을 반환하는 판정 함수입니다. 버튼 비활성화에는 allowed를, 안내문에는 reason을 사용하면 두 UI가 서로 다른 조건을 설명하지 않습니다.

여러 조건이 동시에 안 맞으면 위에서 먼저 검사한 이유가 표시됩니다. 따라서 이유의 표시 순서도 제품 선택입니다. 시작 정책을 모았다고 중지·종료 정책까지 해결된 것은 아닙니다. 각 명령의 허용 조건을 따로 정의해야 합니다.

학습 예제의 입력 상태는 선언한 값만 들어온다고 가정합니다. 실제 API에서 새로운 상태 문자열이 오면 임의로 허용하기보다 지원하지 않는 상태로 처리하고 계약을 확인해야 합니다.

### 프론트와 서버가 각각 맡는 일

프론트는 현재 알고 있는 값으로 불가능한 조작을 줄이고 이유를 안내합니다. 서버는 실제 요청을 받은 시점의 권한·심사·운영 상태로 변경을 허용할지 판단합니다. 버튼을 숨겨도 사용자가 직접 HTTP 요청을 보낼 수 있으므로 서버 검사는 반드시 별도로 필요합니다.

버튼이 활성화된 뒤 다른 운영자가 광고를 종료할 수도 있습니다. 이때 거절 응답은 예상 가능한 상황입니다. 성공한 척 상태를 바꾸지 말고, 거절 이유를 알리고 최신 상태를 다시 확인할 수 있게 합니다. 네트워크 장애와 정책 거절도 같은 이유로 설명하지 않습니다.

### 검증

권한 없음, 미승인, 종료, 이미 운영중은 시작 불가입니다. 승인+PAUSED+권한 있음만 허용합니다. 버튼과 이유 문구가 일치하는지, 서버 거절 후 표시가 원상태인지 확인합니다.

### 면접에서 말하기

> “운영 상태와 심사 상태는 별도 축입니다. 단순 토글 대신 시작 가능한 조건을 함수로 모아 버튼과 설명을 일치시키겠습니다. 최종 전환 가능 여부는 서버가 검사하도록 처리하겠습니다.”

**꼬리질문:** 프론트에서 막았으니 권한 검사를 생략할 수 있는가?

**해설:** 없습니다. UI는 우회할 수 있고 서버 상태도 바뀝니다. 프론트 검사는 안내와 조작 편의, 서버 검사는 실제 변경의 허용 여부를 맡습니다.

## 05. 광고 계정을 바꿨는데 이전 계정 데이터가 보인다

### 개념부터 풀어보기

광고 계정은 데이터를 소유하고 권한을 부여받는 단위입니다. A 계정의 캠페인 17과 B 계정의 캠페인 17은 ID 숫자가 같아도 다른 대상일 수 있습니다. 따라서 ‘어떤 광고인가’는 계정과 캠페인 ID를 함께 보고 판단합니다.

캐시는 이전 조회 결과를 보관해 재사용하는 공간입니다. query key는 그 결과를 찾는 주소 역할을 합니다. `['campaigns']`만 쓰면 계정 A와 B가 같은 주소를 공유합니다. 조회 함수가 accountId를 참조한다는 사실만으로 캐시 주소까지 자동 분리되지는 않습니다.

### 요구사항과 Before

대행사 운영자가 가상 광고 계정 A·B를 전환합니다. 목록·상세·선택 ID·변경 요청 모두 현재 계정에 속해야 합니다. 전환 중 이전 계정 정보를 임시로 표시하지 않는 정책입니다.

```tsx
useQuery({
  queryKey: ['campaigns'],
  queryFn: () => api.listCampaigns(accountId),
});
```

### 재현과 우선순위

A의 조회가 끝난 뒤 B로 전환합니다. 같은 key 때문에 A 캐시를 B 화면에 표시하거나 같은 ID의 상세가 섞일 수 있습니다. 단순 시각 오류를 넘어 잘못된 계정 판단·변경으로 이어질 수 있으므로 먼저 격리합니다. 브라우저에 표시된 것만으로 실제 서버의 계정 간 권한 유출까지 단정하지 않습니다.

### After

```tsx
useQuery({
  queryKey: ['campaigns', accountId, normalizedFilters],
  queryFn: () => api.listCampaigns(accountId, normalizedFilters),
  enabled: Boolean(accountId),
});
// 계정 전환 시 초안·선택 ID·지역 UI 상태를 새 세션으로 시작
<CampaignWorkspace key={accountId} accountId={accountId} />;
```

결과에 영향을 주는 계정과 조건을 key에 넣습니다. key는 캐시 구분이고 접근 권한 검사가 아닙니다. 이전 데이터를 placeholder로 유지하는 옵션이 있다면 계정 전환에서도 노출되는지 별도로 확인합니다. 위 예제에서는 그 옵션을 사용하지 않습니다. [TanStack Query key 가이드](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)

저장 성공 후에는 클릭 때 묶은 `variables.accountId`, `variables.campaignId`의 캐시를 갱신합니다. 완료 시점의 현재 계정에 응답을 쓰면 안 됩니다. 로그아웃·권한 철회 시 캐시 보관 정책도 별도 결정합니다.

### 서로 다른 두 key의 역할

| 코드 | 역할 | 해결하지 않는 것 |
| --- | --- | --- |
| queryKey에 accountId 포함 | 서버 조회 결과를 계정별로 구분 | 입력창·체크박스 같은 지역 상태 초기화 |
| React의 key에 accountId 포함 | 계정 변경 시 편집 화면을 새로 구성 | 서버 캐시 주소와 접근 권한 검사 |

`normalizedFilters`는 허용값과 기본값을 적용한 조회 조건입니다. 예를 들어 누락된 페이지는 1로 바꾸고 허용되지 않은 상태는 ALL로 바꿉니다. 페이지·정렬·기간처럼 응답을 바꾸는 값도 key와 API 인자에 함께 포함해야 합니다. [TanStack Query의 query key 안내](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)

`enabled: Boolean(accountId)`는 계정을 아직 선택하지 않았을 때 조회하지 않게 하는 조건입니다. 계정 접근 권한을 검증하는 장치는 아닙니다. placeholder는 새 결과가 올 때까지 임시로 보여줄 데이터인데, 이 수업에서는 이전 계정 데이터를 그 용도로 쓰지 않습니다.

### 조회 분리만으로 저장까지 안전해지지는 않는 이유

A 예산 저장을 시작하고 B로 이동했다고 가정합니다. 늦게 도착한 A 저장 응답은 A에 속합니다. 완료 시점의 B를 기준으로 캐시를 갱신하면 조회 key를 잘 만들어도 다시 데이터가 섞입니다. 저장 시점의 `variables.accountId`와 `variables.campaignId`로 갱신 대상을 정합니다.

계정 전환 시 초기화할 지역 상태에는 선택한 행, 입력 초안, 열려 있는 상세 패널 등이 있습니다. 초안이 있다면 이동 전에 보관·폐기 정책을 적용해야 하며 key 변경 자체가 그 확인을 대신하지 않습니다. 자세한 초안 처리는 10에서 다룹니다.

검증할 때는 A와 B의 ID를 일부러 같게 하고 이름만 다르게 두세요. ID가 우연히 전부 다르면 계정 경계가 빠진 버그를 놓칠 수 있습니다. 서버 권한 테스트는 ‘B 권한이 없는 사용자가 B ID로 요청해도 거절되는가’를 별도로 확인합니다.

### 검증

A와 B에서 같은 캠페인 ID에 다른 이름을 반환하게 합니다. 계정 전환 뒤 잘못된 이름이 잠깐이라도 보이지 않는지 확인합니다. A의 느린 저장 응답이 B의 캐시를 변경하지 않는지 검사합니다. 서버 통합 테스트에서는 다른 계정 ID를 보낸 요청이 실제로 거절되는지도 확인해야 합니다.

### 면접에서 말하기

> “계정은 캐시와 편집 세션의 경계입니다. key에 계정을 포함하고 전환 시 지역 선택 상태를 초기화하겠습니다. 서버 권한은 별도이며 저장 응답은 제출 당시 계정의 데이터에만 반영하겠습니다.”

**꼬리질문:** 계정을 바꿀 때 모든 캐시를 지우면 되는가?

**해설:** 눈앞의 증상을 줄일 수 있지만 정상적인 캐시 재사용도 없애며 늦은 응답 처리 문제는 남습니다. 우선 데이터 식별과 응답 적용 대상을 정확하게 만들고, 로그아웃 같은 별도 상황의 삭제 정책을 적용합니다.

## 06. 필터를 바꾸자 결과가 없는 것처럼 보인다

### 개념부터 풀어보기

페이지네이션은 전체 결과를 여러 묶음으로 나누어 가져오는 방식입니다. 페이지 크기가 20이고 필터 결과가 120개이면 6페이지입니다. 필터는 그 120개에 포함될 대상을 결정하고, 페이지는 그중 어느 묶음을 볼지 결정합니다.

필터를 바꾸면 전체 결과의 개수도 바뀝니다. 이전 필터의 7페이지가 새 필터에도 존재한다는 보장은 없습니다. 그래서 이 수업에서는 필터 변경을 ‘새 조건의 1페이지로 이동’이라는 하나의 사용자 동작으로 정의합니다.

### 요구사항과 Before

서버 페이지네이션 화면입니다. 필터가 바뀌면 1페이지로 이동하고 정렬은 전체 필터 결과에 적용합니다. URL을 공유하면 같은 조건이 열려야 합니다.

```tsx
const [status, setStatus] = useState('ALL');
const [page, setPage] = useState(7);
// 필터 변경 시 page는 그대로
<select onChange={(event) => setStatus(event.target.value)} />;
```

### 재현과 우선순위

전체 7페이지에서 ACTIVE만 검색했더니 결과가 1페이지만 있습니다. API에 page=7을 보내 빈 결과가 나옵니다. 사용자는 운영 중 광고가 없다고 오인할 수 있습니다. 주요 탐색 경로에서 재현된다면 사소한 컴포넌트 분리보다 우선합니다.

### After: 함께 바뀌는 조건을 한 사건으로

```tsx
type Filters = { status: 'ALL' | 'ACTIVE' | 'PAUSED'; page: number };
const [filters, setFilters] = useState<Filters>({ status: 'ALL', page: 1 });
function changeStatus(status: Filters['status']) {
  setFilters((previous) => ({ ...previous, status, page: 1 }));
}
```

필터 변경과 페이지 초기화를 같은 업데이트에서 표현합니다. `useEffect`로 나중에 페이지를 초기화하면 중간 조건으로 불필요한 조회가 나갈 수 있습니다. 삭제로 마지막 페이지가 비는 경우에는 서버 total을 기준으로 유효 페이지를 조정하는 별도 정책이 필요합니다.

URL을 원본으로 사용할 때는 위 state와 URL을 양방향 Effect로 계속 동기화하지 않습니다. 검증한 URL에서 조건을 만들고 이벤트에서 URL을 갱신하는 경로로 단순화합니다.

```ts
const params = new URLSearchParams(location.search);
const raw = Number(params.get('page') ?? '1');
const page = Number.isSafeInteger(raw) && raw >= 1 ? raw : 1;
```

status도 허용값만 받고 그 외에는 ALL로 정규화합니다. 현재 페이지 20개를 브라우저에서 정렬해 전체 정렬인 것처럼 표시하면 안 됩니다. 서버 정렬 파라미터를 보내거나 전체 데이터를 가진 구조여야 합니다.

### 하나의 업데이트가 필요한 이유

Before는 status만 바꾸고 page는 7로 남깁니다. After는 `{ ...previous, status, page: 1 }`을 한 번에 만들어 새 status와 1페이지를 같은 조회 조건으로 전달합니다. state 개수가 하나여야 좋은 코드라는 뜻은 아닙니다. 요구사항상 함께 바뀌는 값을 일관되게 갱신하는 것이 핵심입니다.

Effect에서 뒤늦게 페이지를 초기화하면 새 status와 옛 page가 조합된 렌더가 생길 수 있습니다. 이를 조회 Hook이 사용하면 불필요한 요청이 발생할 수 있습니다. 테스트는 이 잘못된 조합이 요청되지 않는지를 중심으로 작성합니다. 재시도·개발 모드 등의 영향까지 무시하고 총 요청 횟수가 언제나 1이라고 일반화하지 않습니다.

### URL이 상태 원본이라는 뜻

사용자가 공유한 URL의 status·page를 읽어 화면과 API 조건을 만듭니다. 필터 이벤트는 URL을 바꾸고, 바뀐 URL이 다시 화면을 결정합니다. 이때 똑같은 조건을 별도 state에도 저장하고 양방향 Effect로 맞추면 어느 쪽이 최신인지 불분명해질 수 있습니다.

위 state 예시는 지역 state를 원본으로 쓸 때의 방식이고 URL 예시는 URL을 원본으로 쓸 때의 대안입니다. 두 방식을 그대로 겹쳐 붙이는 예제가 아닙니다. 검색 입력 중인 문자열과 URL에 확정한 검색어처럼 역할이 다른 값은 별도 상태로 둘 수 있습니다.

### 정렬과 페이지 경계

전체 비용 내림차순이면 서버는 ‘필터 → 정렬 → 페이지 자르기’ 순서로 결과를 만들어야 합니다. 첫 페이지의 20개만 정렬하면 다음 페이지에 있는 더 큰 비용의 광고를 맨 위로 올릴 수 없습니다.

비용이 같은 광고는 ID 같은 보조 기준으로 순서를 정합니다. 예를 들어 `비용 내림차순, ID 오름차순`입니다. 다만 정렬 순서를 고정해도 조회 사이에 데이터가 추가·삭제되면 offset 페이지가 움직일 수 있습니다. 보조 키가 동시 변경까지 막아주는 것은 아닙니다.

삭제 후 마지막 페이지가 비면 `max(1, ceil(total / pageSize))`로 마지막 유효 페이지를 계산해 이동할 수 있습니다. total은 현재 필터와 같은 조건의 서버 전체 개수여야 합니다. 0건일 때의 1페이지는 실제 데이터가 있다는 뜻이 아니라 빈 화면의 기본 위치입니다.

### 검증

7페이지 → 필터 변경에서 새 필터와 page=1이 함께 조회 조건이 되는지, 새 필터와 옛 page=7로 잘못 조회하지 않는지 확인합니다. URL 새로고침·뒤로가기·잘못된 page에서 같은 규칙을 적용합니다. 동일 비용 값의 순서는 ID 등 보조 키로 고정하여 동률 항목의 순서가 임의로 바뀌지 않게 합니다.

### 면접에서 말하기

> “필터와 페이지가 독립적으로 바뀌어 유효하지 않은 조합을 조회합니다. 필터 변경 사건에서 페이지도 함께 초기화하겠습니다. 전체 정렬인지 현재 페이지 정렬인지 API 계약도 확인하겠습니다.”

**꼬리질문:** 전체 선택은 현재 페이지인가, 필터 전체인가?

**해설:** 제품 계약을 물어봐야 합니다. 현재 페이지 ID만 가지고 필터 전체를 선택했다고 표시할 수 없습니다. 작업 대상 범위가 금액·운영 상태 변경의 안전성에 연결됩니다.

## 07. 보고 기간을 빠르게 바꾸면 오래된 성과가 표시된다

### 개념부터 풀어보기

응답 순서 경쟁은 ‘요청을 보낸 순서’와 ‘응답이 도착한 순서’가 달라 생깁니다. A를 먼저 요청했다고 A 응답이 먼저 오는 것은 아닙니다. 현재 화면이 B 기간이면 나중에 도착한 A 응답은 더 이상 화면을 바꿀 자격이 없습니다. 이 자격을 여기서는 요청의 소유권이라고 부릅니다.

| 시점 | 사건 | 기대 화면 |
| --- | --- | --- |
| 0ms | A 기간 조회 시작 | A 로딩 |
| 10ms | B 기간으로 변경 | B 로딩 |
| 110ms | B 응답 도착 | B 결과 |
| 800ms | A 응답 도착 | 계속 B 결과 |

Before는 모든 요청이 `setReport`를 실행하므로 마지막에 도착한 A가 B를 덮습니다. A의 오래된 실패 응답이 B의 성공 화면을 오류로 바꾸는 경우도 같은 문제입니다.

### 요구사항과 Before

보고 기간 A 요청은 800ms, B 요청은 100ms 걸립니다. 현재 선택 기간의 데이터만 표시하며 갱신 실패 시 마지막 성공 결과를 보여주더라도 기준 기간과 실패 사실을 명시해야 합니다.

```tsx
useEffect(() => {
  api.report(period).then(setReport);
}, [period]);
```

### 재현과 우선순위

A 직후 B를 선택하고 B→A 순서로 완료시킵니다. 제목은 B인데 숫자는 A가 되면 보고 해석이 틀어집니다. 색상이나 로딩 애니메이션보다 결과의 소속부터 고칩니다.

### After: 요청 key와 데이터 key를 연결

아래는 queryKey 문자열이 계정·기간·필터를 정규화해 식별하며 `api.report`가 이를 인자로 받는다고 가정한 Hook 발췌입니다.

```tsx
useEffect(() => {
  let active = true;
  setView({ key: queryKey, status: 'loading' });
  api.report(queryKey).then(
    (data) => {
      if (active) setView({ key: queryKey, status: 'success', data });
    },
    () => {
      if (active) setView({ key: queryKey, status: 'error' });
    },
  );
  return () => {
    active = false;
  };
}, [queryKey]);
const visible = view.key === queryKey ? view : { key: queryKey, status: 'loading' };
```

이 작은 수정에서는 기간 변경 시 이전 결과를 숨깁니다. Effect 실행 전 렌더에서도 key가 다른 데이터를 표시하지 않습니다. 공용 boolean ref를 새 요청마다 true로 바꾸면 이전 요청도 다시 자격을 얻을 수 있어, 각 Effect의 지역 변수를 씁니다.

같은 기간 재조회 중 기존 결과를 유지하려면 마지막 성공 데이터와 갱신 상태를 분리합니다. “집계 기준 시각”, “갱신 실패, 이전 결과 표시”를 함께 보여줍니다. 재조회 실패를 0 실적으로 바꾸거나 빈 결과라고 표시하지 않습니다.

### After 코드를 한 줄씩 연결하기

`queryKey`는 계정·기간·필터를 합쳐 ‘어떤 결과인가’를 식별하는 문자열입니다. 충돌 없이 일관된 방식으로 만들어야 합니다. 각 Effect 실행은 자신만의 `active` 변수를 만듭니다. 조건 변경이나 unmount 때 cleanup이 이전 실행의 active를 false로 바꾸어, 그 실행의 성공·실패 응답을 모두 무시합니다.

하나의 공용 ref를 매번 true로 되돌리면 이전 응답도 같은 true를 읽을 수 있습니다. 지역 변수는 요청별로 서로 다른 변수를 참조하므로 이전 실행만 비활성화할 수 있습니다. 이처럼 비동기 함수가 자신이 만들어질 때의 변수를 계속 참조하는 성질을 클로저라고 합니다.

`view.key === queryKey` 비교는 별도 역할을 합니다. 조건 변경 후 새 Effect가 실행되기 전 렌더에서도 A 데이터를 B 제목 아래 보여주지 않게 합니다. cleanup으로 늦은 응답을 무시하는 것과 현재 렌더에서 데이터의 소속을 확인하는 것을 함께 적용한 것입니다. [React useEffect 문서](https://react.dev/reference/react/useEffect)

### 같은 조건 재조회는 별도로 생각하기

이 발췌는 key 변경에 따른 조회를 보여줍니다. 같은 key에서 ‘재시도’를 눌러 다시 실행하려면 별도 재조회 트리거나 조회 라이브러리가 필요합니다. 같은 key의 요청 여러 개가 겹칠 수 있다면 실행 번호로 최신 실행을 식별해야 합니다. key만 같다고 모든 응답이 최신인 것은 아닙니다.

이전 성공 결과를 유지하는 제품에서는 데이터와 갱신 상태를 나눕니다. ‘9월 27일 성과, 10:00 집계 / 10:05 갱신 실패, 이전 결과 표시’처럼 숫자의 기준을 설명합니다. 여기서 오래된 데이터는 마지막 성공값이지 0이 아닙니다.

요청 취소는 낭비를 줄이는 수단이고, 응답 무시는 잘못된 화면 변경을 막는 수단입니다. 취소가 서버에서 이미 실행한 작업을 되돌렸다고 가정하지 않습니다. 테스트에서는 A·B Promise를 원하는 순서로 완료시켜 성공과 실패 양쪽의 오래된 응답이 무시되는지 확인합니다.

### 검증

B 성공 뒤 A 성공, B 성공 뒤 A 실패, 최신 요청 실패, 실패 후 재시도를 검사합니다. 실제 시간을 기다리기보다 수동 완료 가능한 Promise로 순서를 제어합니다. 요청 무시와 취소는 구분하며 취소가 서버 작업까지 되돌린다고 가정하지 않습니다.

### 면접에서 말하기

> “기간 제목과 데이터가 같은 요청에 속한다는 불변식을 먼저 지키겠습니다. 이전 요청의 성공과 실패 모두 화면 변경 권한을 제거하고 역순 응답으로 재현하겠습니다.”

**꼬리질문:** debounce를 넣으면 해결되는가?

**해설:** 요청 수를 줄일 수 있지만 이미 시작된 요청의 순서 문제는 해결하지 않습니다. 응답 적용 대상 식별이 필요합니다.

## 08. 일괄 중지의 일부 성공과 실패를 구분하지 못한다

### 개념부터 풀어보기

이 수업의 일괄 중지는 하나의 큰 트랜잭션이 아니라 광고마다 독립적인 중지 요청을 보내는 작업입니다. A가 성공해도 B는 실패할 수 있습니다. ‘원자적 일괄 작업’은 모두 적용되거나 아무것도 적용되지 않는 별도 서버 보장을 뜻합니다.

`Promise.all`은 하나가 reject하면 전체 대기를 reject하지만 이미 시작한 나머지 요청을 취소하지 않습니다. 제시된 Before도 B가 reject하면 성공 토스트까지 실행되지는 않습니다. 핵심 결함은 이 코드에 개별 결과를 수집하고 보여주는 흐름이 없다는 점입니다. API가 업무상 거절을 fulfilled로 반환하는데 검사하지 않는 경우에는 잘못된 전체 성공 표시까지 생길 수 있습니다.

### 요구사항과 Before

같은 계정의 광고 A·B·C를 중지합니다. 각각 독립적인 서버 작업입니다. A·C는 중지되고 B는 명시적으로 거절될 수 있습니다. 성공한 대상은 재시도하지 않습니다.

```ts
await Promise.all(selectedIds.map((id) => api.pause(id)));
setSelectedIds([]);
showToast('모두 중지했습니다.');
```

### 재현과 우선순위

B만 거절시키면 Promise.all이 reject하지만 A·C 작업은 자동으로 취소되지 않습니다. catch에서 “모두 실패”라고 표시하고 전체 재시도해도 사실과 다릅니다. 중지를 요청한 광고가 계속 운영될 수 있어 결과를 정확히 알리는 일을 우선합니다.

### After

```ts
const ids = [...selectedIds]; // 클릭 시 작업 대상을 고정
const results = await Promise.allSettled(ids.map((id) => api.pause(id)));
const outcomes = results.map((result, index) => ({
  id: ids[index],
  state:
    result.status === 'fulfilled'
      ? 'success'
      : isExplicitRejection(result.reason)
        ? 'rejected'
        : 'unknown',
}));
```

API가 HTTP 비정상 응답을 throw하고 성공 응답을 확인한다는 계약입니다. fetch는 HTTP 500만으로 Promise를 reject하지 않으므로 API 계층이 상태를 검사해야 합니다. `allSettled`는 결과를 모을 뿐 동시 요청 수를 제한하지 않습니다.

결과 UI에는 성공 2건, 거절 1건처럼 사실을 표시합니다. 네트워크 끊김은 서버에서 성공했는지 모를 수 있으므로 결과 불명으로 두고 재조회합니다. 실패 항목 재시도도 작업이 멱등적인지 확인해야 합니다. “중지 상태로 설정”과 “현재 상태 반전”은 재시도의 효과가 다릅니다.

### 세 가지 결과를 구분하기

| 결과 | 확인된 사실 | 후속 동작 |
| --- | --- | --- |
| success | 서버가 중지 성공을 확인함 | 성공 표시, 재시도 대상에서 제외 |
| rejected | 서버가 적용하지 않았음을 명시적으로 확인함 | 이유 표시, 원인 해결 뒤 재시도 검토 |
| unknown | 서버 적용 여부를 확인하지 못함 | 상태나 작업 이력 재조회 |

모든 HTTP 오류를 rejected로 분류하면 안 됩니다. 서버 내부 오류가 변경 전 발생했는지 변경 후 발생했는지 모를 수 있습니다. `isExplicitRejection`은 ‘미적용이 보장되는 오류’라는 API 계약을 기준으로 구현해야 합니다. 네트워크 단절과 타임아웃은 보통 적용 여부를 확정할 수 없습니다.

### After의 실행 순서

1. `[...selectedIds]`로 클릭 시점의 대상 목록을 복사합니다.
2. 각 대상에 중지 요청을 보냅니다.
3. `allSettled`로 성공·실패가 모두 끝날 때까지 기다립니다.
4. 결과는 완료 순서가 아니라 입력 순서로 반환되므로 `ids[index]`로 원래 대상과 연결합니다.
5. UI에는 결과별 개수와 항목별 이유를 보여주고 성공한 항목을 재시도 대상에서 뺍니다.

실제 구현은 ID뿐 아니라 accountId도 제출 시점에 고정해야 합니다. 작업 중 선택 변경을 허용한다면 새로 선택한 행까지 완료 콜백에서 지우지 않도록 선택 상태 갱신 정책도 필요합니다.

‘멱등적’이라는 말은 같은 요청을 반복해도 의도한 최종 상태가 중복으로 변하지 않는다는 뜻입니다. ‘PAUSED로 설정’은 반복해도 PAUSED지만 ‘현재 상태 반전’은 두 번 실행하면 원상태가 될 수 있습니다. 로그·알림 같은 부수 효과의 중복까지 방지되는지는 별도 계약입니다.

allSettled는 동시 실행 개수를 제한하지 않습니다. 1,000개 ID에 바로 map하면 1,000개 요청을 시작할 수 있습니다. 요청 제한이나 서버 bulk API가 필요한지는 규모와 서버 계약으로 판단합니다. 끝나지 않는 요청이 있으면 전체 결과도 늦어지므로 타임아웃과 진행 상태도 정의해야 합니다.

### 검증

일부 성공·전부 성공·명시적 거절·결과 불명을 나눕니다. 작업 시작 후 선택이 바뀌어도 ID와 결과 매칭이 유지돼야 합니다. 성공한 항목은 실패 재시도에 포함하지 않습니다. 수천 개 대상은 서버 bulk API 또는 동시 실행 제한을 고려합니다.

### 면접에서 말하기

> “일괄 작업은 부분 성공이 가능합니다. 제출 대상 ID를 고정하고 개별 결과를 수집하겠습니다. 타임아웃은 확정 실패와 구분해 재조회하고, 성공한 대상까지 무조건 재시도하지 않겠습니다.”

**꼬리질문:** allSettled로 바꾸면 일괄 작업이 원자적이 되는가?

**해설:** 아닙니다. 전체 성공 또는 전체 취소가 필요하면 서버 트랜잭션이나 별도 작업 계약이 필요합니다. 프론트 Promise 조합으로 되돌림을 보장할 수 없습니다.

## 09. 하루 리포트에 자정 근처 비용이 빠진다

### 개념부터 풀어보기

‘2026-09-27’은 달력 날짜이고 ‘2026-09-26T15:00:00.000Z’는 특정 시각입니다. 날짜 하나를 조회 구간으로 바꾸려면 어느 시간대의 하루인지 먼저 정해야 합니다. Z는 UTC 기준이라는 뜻이고 +09:00은 UTC보다 9시간 빠르다는 뜻입니다.

한국의 9월 27일 00:00과 UTC의 9월 26일 15:00은 같은 순간입니다. ISO 문자열에서 날짜가 하루 전으로 보인다고 잘못 변환된 것이 아닙니다.

### 요구사항과 Before

학습용 리포트는 Asia/Seoul 날짜 기준입니다. 2026-09-27 하루는 해당 지역 00:00부터 다음 날 00:00 직전까지입니다. API는 UTC ISO 문자열의 `[from, to)` 구간을 받습니다.

```ts
const from = new Date('2026-09-27').toISOString();
const to = new Date('2026-09-27T23:59:59').toISOString();
```

### 재현과 우선순위

첫 문자열은 UTC 자정 기준이고, 두 번째는 실행 환경의 로컬 시간대에 의존합니다. 기준이 섞일 수 있습니다. 밀리초 단위의 마지막 데이터도 23:59:59 종료값에서 빠집니다. 비용 합계가 달라지므로 집계 정확성 문제로 다룹니다.

### After

아래 코드는 이미 검증된 실제 달력 날짜를 입력받으며 현대 한국 시간(+09:00)만 지원하는 수업용 예제입니다.

```ts
const start = new Date('2026-09-27T00:00:00+09:00');
const end = new Date('2026-09-28T00:00:00+09:00');
const range = { from: start.toISOString(), to: end.toISOString() };
// from: 2026-09-26T15:00:00.000Z
// to:   2026-09-27T15:00:00.000Z
const inRange = (time: number) => time >= start.getTime() && time < end.getTime();
```

끝을 제외하는 구간은 인접 날짜에서 중복·누락을 피하기 쉽습니다. 마지막 시각을 23:59:59.999로 추측해 만드는 대신 다음 날 시작을 사용합니다. 서버도 같은 경계 규칙이어야 합니다.

하루를 무조건 24시간 더하는 코드는 일광절약시간이 있는 지역에 일반화할 수 없습니다. 다국가 제품에서는 서버가 제공한 경계나 시간대 지원 라이브러리를 사용하고 해당 지역의 전환일을 검사합니다. 예제의 +09:00 정책을 세계 공통 규칙으로 외우지 않습니다.

### 반열린 구간을 풀어 읽기

`[from, to)`는 시작은 포함하고 끝은 제외한다는 표기입니다. 즉 `from <= 데이터 시각 < to`입니다. 27일 보고서는 27일 00:00부터 28일 00:00 직전까지이고, 28일 보고서는 그 28일 00:00부터 시작합니다.

| 한국 시각 | 27일 보고서 포함 여부 |
| --- | --- |
| 26일 23:59:59.999 | 제외 |
| 27일 00:00:00.000 | 포함 |
| 27일 23:59:59.999 | 포함 |
| 28일 00:00:00.000 | 제외, 다음 날에 포함 |

종료를 23:59:59로 지정하면 그 뒤의 밀리초 데이터가 빠집니다. 다음 날 시작을 제외하면 저장소의 더 세밀한 시간 정밀도에도 ‘마지막 순간’을 추측할 필요가 없습니다. 서버의 비교 연산도 끝을 제외해야 같은 결과가 나옵니다.

### Date 코드에서 헷갈리기 쉬운 점

JavaScript의 표준 날짜 전용 문자열은 UTC 기준으로 해석됩니다. 시간대 없는 날짜·시간 문자열은 실행 환경의 로컬 시간대로 해석됩니다. 따라서 Before의 두 입력은 기준이 다를 수 있습니다. `toISOString()`은 이미 만들어진 시각을 UTC 문자열로 표현할 뿐, 처음부터 한국 자정으로 다시 해석해 주지 않습니다. [MDN Date 문서](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date)

`getTime()`은 시각을 밀리초 숫자로 바꾸므로 같은 기준의 숫자끼리 구간을 비교할 수 있습니다. 입력 날짜는 변환 전에 검사합니다. 잘못된 달력값을 일부 입력 형식에서 자동 보정할 수 있기 때문에 Date 객체가 만들어졌다는 사실만으로 날짜가 올바르다고 판단하지 않습니다.

일광절약시간(DST)을 쓰는 지역에서는 시계를 앞뒤로 조정하는 날이 있어 달력상 하루가 항상 24시간은 아닙니다. ‘해당 지역 다음 날짜의 자정’과 ‘24시간 뒤’를 구분해야 합니다. 이 예제의 현대 한국 시간 고정 오프셋은 그 지역·기간에 한정한 단순화입니다.

조회 기간이 같아도 늦게 들어온 성과가 추가되면 값이 달라질 수 있습니다. 기간은 **어느 때 발생한 데이터를 고르는지**, 집계 기준 시각은 **언제까지 반영된 집계를 보는지**를 설명합니다.

### 검증

시작 정각 포함, 시작 1ms 전 제외, 끝 1ms 전 포함, 끝 정각 제외를 확인합니다. 2월 30일 같은 잘못된 날짜를 JS가 자동 보정해 유효한 날짜로 받아들이지 않도록 입력 달력값을 검사합니다. 브라우저 시간대가 달라도 ISO 결과는 같아야 합니다.

### 면접에서 말하기

> “날짜 선택값과 API 시각의 기준이 다릅니다. 보고서의 시간대를 먼저 확인하고 다음 날 자정을 제외하는 구간으로 바꾸겠습니다. 경계 직전·정각과 다른 실행 시간대에서 검증하겠습니다.”

**꼬리질문:** 오늘 수치가 나중에 바뀌면 시간대 버그인가?

**해설:** 늦은 집계·정정·전환 귀속 등 다른 원인일 수 있습니다. 조회 구간과 집계 기준 시각을 분리하고, 서버 응답과 비교해 어느 단계에서 차이가 생기는지 확인합니다.

## 10. A 광고의 입력 초안이 B 광고에 저장된다

### 개념부터 풀어보기

초안의 소유권은 ‘이 입력값은 어느 계정의 어느 광고를 수정하려고 쓴 값인가’를 뜻합니다. A에 입력한 20만원은 숫자만 있는 것이 아니라 A를 대상으로 한 사용자 의도입니다. 선택 항목이 B로 바뀌었다고 이 의도가 자동으로 B의 것이 되면 안 됩니다.

같은 위치의 같은 Editor가 유지되면 React는 그 컴포넌트의 state를 보존합니다. props의 campaign이 A에서 B로 바뀌어도 `raw`를 B 예산으로 자동 초기화하지 않습니다. 일반 인자 표현식인 `String(campaign.dailyBudget)`은 렌더 때 다시 평가될 수 있지만, 그 값이 기존 state를 다시 초기화하지는 않습니다. [React 상태 보존과 초기화](https://react.dev/learn/preserving-and-resetting-state)

### 요구사항과 Before

광고 상세 편집기를 다른 항목으로 바꾸면 새 항목의 초기값을 보여줍니다. 미저장 변경이 있으면 이동 전에 유지·폐기 여부를 묻는 제품 정책입니다. 재조회 응답은 편집 중 초안을 자동으로 덮지 않습니다.

```tsx
function Editor({ campaign }: Props) {
  const [raw, setRaw] = useState(String(campaign.dailyBudget));
  async function save() {
    await api.saveBudget(campaign.id, Number(raw));
  }
  // 입력 UI 생략
}
```

### 재현과 우선순위

A에서 20만원을 입력한 뒤 같은 Editor 인스턴스에 B props를 전달합니다. useState에 전달한 초기값으로 기존 state가 다시 설정되지 않으므로 A 초안과 B ID가 조합될 수 있습니다. 다른 광고에 쓰기가 발생하는 경로이므로 우선 차단합니다.

### After: 편집 세션 경계

```tsx
// 부모에서 미저장 변경 확인을 통과한 뒤 selected를 교체
<Editor key={`${accountId}:${selected.id}`} campaign={selected} />
```

계정과 ID를 key로 세션을 구분합니다. key 변경은 하위 상태를 초기화하므로 미저장 확인은 부모에서 먼저 해야 합니다. 모든 props 변경마다 Effect로 초안을 덮으면 주기적 재조회가 사용자의 타이핑을 지울 수 있습니다.

```ts
// 저장 핸들러에서 값의 소속을 함께 고정하는 발췌
const command = { accountId, campaignId: campaign.id, raw, version: campaign.version };
```

이후 저장 완료 처리는 command가 속한 항목을 갱신합니다. 이미 떠난 편집기에 응답을 표시하지 않습니다. 사용자가 계속 타이핑할 수 있는 정책이라면 제출 초안과 현재 초안의 변경 여부도 비교해야 합니다.

### 문제가 생기는 정확한 조합

| 단계 | campaign.id | raw |
| --- | --- | --- |
| A 선택 | A | A의 서버 예산 |
| A에서 20만원 입력 | A | 200000 |
| 같은 Editor에 B props 전달 | B | 여전히 200000 |
| 저장 | B로 요청 | A에서 작성한 200000 전송 |

그래서 새 항목 선택은 새 편집 세션으로 취급합니다. 계정과 광고 ID로 key를 바꾸면 새 Editor의 state가 새로 만들어집니다. 버전까지 key에 넣으면 같은 광고의 서버 갱신에도 입력이 사라질 수 있으므로 항목 변경과 재조회를 구분합니다.

### 미저장 확인과 key의 순서

1. 사용자가 B를 선택하려고 합니다.
2. 부모가 A의 미저장 변경 여부를 확인합니다.
3. 이동 취소이면 A와 초안을 그대로 둡니다.
4. 폐기 후 이동이면 selected를 B로 바꿉니다.
5. 새 key의 Editor가 B의 초기값으로 열립니다.

‘초안을 유지한 채 B로 이동’하는 정책이라면 key로 초기화하기 전에 계정·광고별 외부 저장소에 초안을 보관해야 합니다. key만 바꿔서는 폐기한 state를 복원할 수 없습니다. 이 수업의 최소 구현은 이동 취소 또는 폐기 후 이동입니다.

### 재조회와 저장 완료도 초안을 덮을 수 있다

같은 A를 재조회했을 때 모든 props 변경을 입력창에 복사하면 타이핑 중인 값이 사라집니다. 편집을 시작할 때의 기준 버전과 서버 최신값을 구분하고, 변경 알림이나 명시적 다시 불러오기로 처리할 수 있습니다. 입력은 옛 값인데 expectedVersion만 최신값으로 바꾸면 03의 충돌 보호가 무력화될 수 있습니다.

저장 중에도 추가 입력을 허용하면 또 다른 상황이 생깁니다. 20만원 저장을 시작한 뒤 25만원으로 고쳤는데 20만원 성공 응답이 오면, 서버 확정값은 20만원이지만 현재 초안은 25만원이어야 합니다. 제출 후 입력 변경 여부를 별도로 기록해 새 초안을 지우지 않거나, 저장 중 입력을 잠그는 정책을 선택합니다.

### 검증

A 편집→B 선택 시 폐기 취소와 승인 두 경로를 검사합니다. A 저장 대기 중 B 이동이 허용된다면 늦은 응답이 B에 반영되지 않는지 확인합니다. 같은 A의 서버 재조회에서 초안을 보존하는지 별도로 검사합니다.

### 면접에서 말하기

> “초안의 소유자는 광고 ID입니다. 선택 변경으로 props만 교체되어 다른 광고의 ID와 기존 초안이 섞입니다. 편집 세션을 계정·ID로 구분하고 저장 명령의 대상도 제출 시점에 고정하겠습니다.”

**꼬리질문:** key에 version도 넣으면 안전한가?

**해설:** 재조회로 version이 변할 때마다 초안을 버릴 수 있습니다. 새 항목 선택과 같은 항목의 서버 갱신은 다른 사건이므로 동일한 초기화 정책을 쓰지 않습니다.

## 11. 검색할 때 대량 테이블이 멈춘다

### 개념부터 풀어보기

n은 소재 수, m은 성과 행 수입니다. Before의 `find`는 원하는 ID를 만날 때까지 성과 배열을 앞에서부터 찾습니다. 이를 소재마다 반복하면 최악에는 n×m번 수준의 비교를 하므로 O(n×m)이라고 표현합니다. 20,000개씩이면 최대 약 4억 번 규모가 될 수 있으며 실제 비교 횟수는 매칭 위치에 따라 달라집니다.

After는 성과 m개로 Map을 한 번 만들고 소재 n개에서 ID로 조회합니다. 일반적인 Map 구현의 평균 조회 비용을 가정하면 O(n+m) 수준으로 줄어듭니다. 정확한 실행 시간 보장은 아니며 Map을 위한 추가 메모리도 사용합니다.

### 요구사항과 Before

학습용 데이터는 최대 20,000개 소재이며 ID는 유일합니다. 이름과 비용을 결합하고 검색·정렬합니다. 숫자는 연습용 상한이며 토스의 실제 데이터 규모가 아닙니다.

```ts
const rows = creatives.map((creative) => ({
  ...creative,
  spendWon: metrics.find((metric) => metric.id === creative.id)?.spendWon ?? null,
}));
```

### 재현과 우선순위

큰 데이터에서 타이핑 지연을 측정합니다. 매 입력마다 n개 항목에서 m개 성과를 찾으면 O(n×m) 비용입니다. 하지만 네트워크 지연·필터 계산·React 렌더·브라우저 레이아웃 중 실제로 무엇이 느린지 먼저 측정해야 합니다.

작업 자체가 멈출 정도면 성능도 높은 우선순위입니다. 데이터가 틀리거나 잘못된 광고 변경이 동시에 있다면 정확성 보호를 먼저 하고 성능을 이어서 해결하는 식으로 범위를 협의합니다.

### After

```ts
const byId = new Map(metrics.map((metric) => [metric.id, metric]));
const rows = creatives.map((creative) => ({
  ...creative,
  spendWon: byId.get(creative.id)?.spendWon ?? null,
}));
```

색인을 한 번 만들면 일반적인 Map 조회 비용을 가정해 전체 결합을 O(n+m) 수준으로 줄입니다. 입력 데이터가 바뀌지 않았다면 이 결합을 매 키 입력마다 다시 할 필요도 없습니다. 결과가 같은지 테스트하고 측정 전후 시간을 비교합니다.

### 해결책마다 다른 대상

| 방법                   | 줄이는 비용           | 해결하지 않는 것              |
| ---------------------- | --------------------- | ----------------------------- |
| 색인·한 번만 합계 계산 | 반복 계산             | DOM 수                        |
| useMemo                | 같은 입력의 재계산    | 첫 계산·새 입력 계산          |
| 가상화                 | 화면 밖 DOM 렌더      | 전체 정렬 계산                |
| debounce               | 처리 빈도             | 한 번의 무거운 계산·응답 순서 |
| Worker                 | 메인 스레드 계산 부담 | 데이터 전달 비용·전체 계산량  |
| 서버 조회              | 브라우저 메모리·계산  | 네트워크 대기·서버 부하       |

Worker로 옮겨도 결과 순서가 바뀔 수 있습니다. 메시지에 requestId를 붙여 최신 요청 결과만 적용합니다. 데이터 복제·전달 비용, 메모리 상한, Worker 실패 복구도 설계해야 합니다. 전체 다운로드는 상한과 권한이 확인된 경우에만 선택합니다.

### 느리다는 증상을 단계로 나누기

| 관찰 | 먼저 측정할 대상 | 가능한 수정 |
| --- | --- | --- |
| 요청 후 데이터 도착이 늦음 | 네트워크·서버 응답 시간 | 응답 크기·조회 조건·서버 처리 |
| 데이터는 왔는데 입력이 멈춤 | 결합·검색·정렬 계산 | 색인, 중복 계산 제거 |
| 계산 뒤 화면 표시가 오래 걸림 | React 렌더·DOM·레이아웃 | 행 가상화, 불필요한 렌더 감소 |

예를 들어 결합 전후에 `performance.now()`를 읽어 계산 시간을 재고, 브라우저 성능 도구와 React Profiler로 렌더 구간을 따로 봅니다. 같은 데이터 크기와 장치에서 여러 번 측정하고 첫 로딩과 반복 검색을 구분해야 비교할 수 있습니다.

### 자주 나오는 해결책을 풀어 설명하기

**useMemo**는 의존 입력이 같을 때 이전 계산 결과를 재사용합니다. 새로운 배열을 매번 만들면 의존성이 달라져 계산이 반복될 수 있고, 첫 계산 자체가 빨라지는 것도 아닙니다. 정확성을 useMemo에 의존하지 말고 반복 계산 비용을 줄일 때 사용합니다.

**가상화**는 20,000개 행 중 화면 주변의 일부만 DOM으로 만듭니다. DOM은 브라우저가 실제로 표시할 문서 요소입니다. 전체 검색·정렬에 필요한 계산까지 자동으로 줄이지는 않습니다.

**debounce**는 입력이 잠시 멈춘 뒤 작업을 시작해 빈도를 줄입니다. 한 번 실행할 때 오래 걸리는 문제는 남습니다. 사용자가 입력하는 글자 자체까지 늦게 표시할 필요는 없으며, 입력과 검색 실행 시점을 분리할 수 있습니다.

**Worker**는 계산을 메인 스레드 밖에서 실행합니다. 메인 스레드는 사용자 입력과 화면 표시도 처리하므로 무거운 계산이 여기에 있으면 조작이 지연됩니다. Worker로 옮겨도 총 계산이 없어지는 것은 아니고 데이터 전달·복제와 결과 적용 비용이 생깁니다.

Worker 요청에도 번호를 붙입니다. 오래된 검색 결과가 늦게 도착하면 최신 검색 화면을 덮지 않도록 07과 같은 원리를 적용합니다. Worker 종료나 실패 시 로딩이 영원히 남지 않는 복구 처리도 필요합니다.

**서버 처리**는 브라우저가 전체 데이터를 보유하기 어려울 때 유용합니다. 대신 매 검색의 네트워크 대기가 생길 수 있습니다. 실제 상한·응답 크기·변경 빈도·접근 권한을 확인해서 선택합니다. 어떤 도구를 썼는지보다 측정된 병목이 줄고 결과가 유지되는지가 검증 기준입니다.

### 검증

같은 데이터·장치·조건에서 최초 로딩과 반복 검색 시간을 나누어 측정합니다. 작은 데이터에서 빠르다는 사실만으로 개선됐다고 결론 내리지 않습니다. 정렬 결과·누락 항목·안정적인 행 ID가 유지되는지도 확인합니다.

### 면접에서 말하기

> “먼저 계산과 렌더 시간을 분리해 측정하겠습니다. 반복 find가 병목이면 색인을 만들어 변경 범위를 줄이고, DOM이 병목일 때 가상화를 검토하겠습니다. Worker를 넣는 것 자체를 목표로 삼지는 않겠습니다.”

**꼬리질문:** 서버 처리와 클라이언트 처리 중 정답은?

**해설:** 데이터 상한, 응답 크기, 변화 빈도, 보안 경계, 사용자 탐색 패턴에 따라 선택합니다. 한 제품의 선택을 모든 운영툴에 적용할 수 없습니다.

## 12. 내보낸 보고서가 화면 조건과 다르다

### 개념부터 풀어보기

화면의 페이지는 전체 결과 중 일부입니다. 내보내기 요구사항이 ‘필터에 맞는 전체’라면 현재 페이지 배열만 CSV로 만들 수 없습니다. CSV는 표의 행과 열을 텍스트로 저장하는 형식입니다. 파일이 만들어졌다는 사실만으로 내용이 완전하다고 판단하지 않습니다.

job은 서버가 오래 걸리는 작업을 식별·추적하는 단위입니다. 생성 응답의 job ID는 작업 접수를 뜻하며 파일 완성을 뜻하지 않을 수 있습니다. 이 수업에서는 그 ID로 상태를 반복 조회하는 폴링을 사용합니다.

### 요구사항과 Before

현재 페이지가 아니라 현재 필터에 맞는 전체 결과를 내보냅니다. 내보내기 버튼을 누른 시점의 계정·기간·조건을 작업에 고정합니다. 서버 job ID로 완료를 확인합니다.

```ts
downloadCsv(currentPageRows);
```

### 재현과 우선순위

조건에 맞는 광고가 120개인데 첫 페이지 20개만 내려받습니다. 사용자는 전체 보고서라고 생각할 수 있습니다. 외부 보고와 수치 비교에 사용되는 기능이라면 데이터 완전성 문제입니다. 서버가 전체 결과를 내보내는 API를 제공하는지 먼저 확인합니다.

### After: 전체 결과와 조건을 서버 작업에 고정

```ts
// page를 내보내기 계약에서 제외. 조건은 원시값으로 복사
const snapshot = {
  accountId,
  from: filters.from,
  to: filters.to,
  status: filters.status,
  keyword: filters.keyword,
};
const job = await api.createExport(snapshot);
setExportJob({ id: job.id, snapshot });
```

화면 필터가 바뀌어도 이미 시작한 작업의 라벨·파일명은 snapshot 기준입니다. 응답 시점의 최신 필터로 파일명을 만들지 않습니다. “버튼 시점 조건”을 고정해도 그 사이 서버 데이터 자체가 바뀔 수 있습니다. 정확한 데이터 스냅샷이 필요하면 서버가 기준 시각·버전까지 보장해야 합니다.

폴링은 같은 요청이 끝나기 전에 다음 요청이 겹치지 않게 합니다. done·failed에서 중지하고 unmount·계정 변경에서도 정리합니다. 알려지지 않은 status는 영원히 로딩으로 두지 말고 응답 계약 오류로 처리합니다. 다운로드 권한은 서버가 검사합니다.

### 두 종류의 스냅샷을 구분하기

| 구분 | 고정하는 것 | 예시 |
| --- | --- | --- |
| 조건 스냅샷 | 클릭 당시 계정·기간·필터 | 9월 27일 ACTIVE 광고 전체 |
| 데이터 스냅샷 | 특정 시점의 실제 데이터 내용 | 10:00에 확정된 성과와 상태 |

코드의 snapshot은 첫 번째입니다. 10:00에 작업을 요청하고 10:01에 서버가 조회하는 동안 광고 상태가 바뀌면 대상이나 성과가 달라질 수 있습니다. 버튼 시점 데이터까지 고정해야 한다면 서버가 조회 버전이나 일관된 기준 시각을 보장해야 합니다.

조건 값을 각각 복사하는 것은 이후 filters 변경이 기존 작업에 영향을 주지 않게 하기 위함입니다. 이 예시의 필드는 문자열 같은 원시값입니다. 배열·중첩 객체 필터를 추가하면 참조 공유와 변경 가능성을 따로 확인해야 합니다.

page를 뺀 이유는 현재 페이지만 내보내는 작업이 아니기 때문입니다. 내보내기 순서까지 화면과 같아야 한다면 정렬 조건도 고정해 전달해야 합니다. 표시할 열이나 통화도 결과에 영향을 준다면 작업 계약에 포함합니다.

### 폴링의 시작과 끝

1. 클릭 당시 조건으로 작업을 생성합니다.
2. 반환된 job ID와 그 조건을 함께 저장합니다.
3. 작업이 진행 중이면 상태를 조회합니다.
4. 조회가 끝난 뒤 일정 간격 후 다음 조회를 예약합니다.
5. done이면 다운로드 단계로, failed이면 실패 안내로 이동하고 반복을 멈춥니다.

일정 간격마다 무조건 요청하는 방식은 느린 응답에서 요청이 겹칠 수 있습니다. 화면을 닫거나 계정을 바꾸면 타이머를 정리하고 이미 진행 중인 응답도 이전 화면에 적용되지 않게 해야 합니다. 타이머 제거만으로 이미 보낸 요청의 응답이 없어지지는 않습니다.

조회 중단이 서버 파일 생성 취소를 뜻하지는 않습니다. 취소가 필요하면 서버 취소 API가 별도로 있어야 합니다. 폴링 통신 실패와 job 자체의 failed도 다릅니다. 통신 실패 시 서버 작업은 계속될 수 있으므로 제한된 재조회·재시도 정책을 정의합니다.

이 발췌는 한 번에 한 작업만 생성하는 화면을 전제로 합니다. 여러 작업을 허용하면 하나의 setExportJob 값으로 덮어쓰기보다 job별 상태를 관리해야 합니다. 늦은 생성 응답도 제출 당시 계정에 속하도록 처리합니다.

검증에서는 화면 라벨만 보지 말고 실제 파일의 행 수·조건·집계 기준 시각을 확인합니다. 다운로드 URL을 안다고 권한을 우회할 수 없어야 하므로 파일 접근 시 서버 권한도 검사해야 합니다.

### 검증

전체 120개가 대상인지, 페이지 파라미터가 전달되지 않는지, 시작 후 필터를 바꿔도 job의 조건이 유지되는지 확인합니다. 완료·실패 후 더 이상 폴링하지 않는지, 이전 계정의 job 응답이 새 계정 화면에 연결되지 않는지 검사합니다. 실제 파일 행 수와 집계 기준 시각도 별도 통합 검증 대상입니다.

### 면접에서 말하기

> “화면 페이지 데이터는 전체 내보내기 범위와 다릅니다. 서버 작업에 클릭 시점 조건을 고정하고 작업 상태와 화면 조회 상태를 분리하겠습니다. 파일 내용의 기준 시각까지 일치해야 하는지는 추가로 확인하겠습니다.”

**꼬리질문:** 버튼만 disabled면 끝인가?

**해설:** 중복 클릭만 줄일 뿐 조건 불일치·전체 범위·계정 권한·폴링 정리는 해결되지 않습니다. 작업의 입력, 소유 계정, 수명과 결과 계약을 함께 정의해야 합니다.

### 재현한 사실과 추정 분리

```text
관찰: A에서 입력한 금액이 B ID를 담은 요청으로 전송됨
기대: 저장 대상과 초안의 소유 광고가 같아야 함
영향: 다른 광고 예산을 변경할 가능성
미확인: 서버가 version/권한 조건으로 이 요청을 거절하는가
우선 조치: ID별 편집 세션 분리와 제출값 고정
검증: A→B 이동, A의 늦은 응답, 같은 A 재조회
```

### 우선순위를 설명하는 구체적인 방법

‘금액 버그니까 무조건 1순위’라고 말하기보다 어떤 입력이 어디에 반영되는지 확인합니다. A 초안이 B ID로 전송되는 상황은 잘못된 대상 변경 경로가 재현된 것입니다. 반면 실제 서버 저장 여부를 아직 보지 않았다면 ‘B 예산이 이미 바뀌었다’고 단정하지 않습니다.

판단에는 영향의 크기, 되돌리기 쉬운지, 현재 재현되는지, 다른 수정의 선행 조건인지, 남은 시간이 함께 들어갑니다. 예를 들어 저장 성공 표시를 먼저 고쳐야 뒤이은 예산 검증 결과를 신뢰할 수 있다면 선행 관계도 수정 순서의 근거가 됩니다.

최소 수정은 줄 수가 가장 적은 수정이 아닙니다. 계정 경계를 바로잡는 데 query key와 저장 응답 처리 두 곳이 필요하면 둘 다 바꾸어야 합니다. 반대로 관련 없는 상태 라이브러리 교체는 현재 결함을 해결하는 데 필요하지 않다면 미룹니다.

### 테스트를 구체적으로 말하는 방법

‘비동기 테스트를 하겠습니다’보다 다음처럼 입력·순서·관찰 결과를 정합니다.

| 사례 | 의도적으로 만드는 조건 | 확인할 결과 |
| --- | --- | --- |
| 07 응답 역전 | A 요청 후 B 요청, B부터 성공 | 화면은 B 유지, 뒤늦은 A 무시 |
| 03 충돌 | 서버는 버전 8, 제출은 버전 7 | 충돌 안내, 초안 유지, 자동 덮어쓰기 없음 |
| 08 부분 성공 | A 성공, B 미적용 거절, C 타임아웃 | 세 결과 구분, A 재시도 제외, C 결과 확인 |
| 10 초안 이동 | A에 입력 후 B 이동 취소 | A 선택과 A 입력 유지 |

수정 전 테스트가 실패할 때도 실패 원인을 봅니다. import 오류로 실패했다면 사용자 결함을 재현한 것이 아닙니다. 테스트 준비를 고친 뒤 의도한 잘못된 동작 때문에 실패하는지 확인합니다. 수정 후에는 동일 재현 테스트와 관련된 정상·실패·재시도 경로를 실행합니다.

단위 테스트는 작은 함수의 계산을, 컴포넌트 테스트는 화면 조작과 표시를, 서버 통합 테스트는 실제 API·저장소의 계약을 확인합니다. 하나가 통과했다고 나머지도 통과했다고 말하지 않습니다. 타입 검사는 자료형의 일관성을, 린트는 정해 둔 코드 규칙을 확인하며 업무 정책의 정확성을 대신 보장하지 않습니다.

### 고치기 전·중·후에 할 말

**고치기 전:** “세 가지 문제를 확인했습니다. 다른 광고에 저장될 수 있는 경로를 먼저 고치겠습니다. 실제 서버 적용 여부는 아직 미확인이지만 제출 대상과 초안이 불일치하는 것은 재현했습니다.”

**고치는 중:** “지금은 상태 라이브러리를 바꾸지 않고 세션 경계와 제출 대상만 고정하겠습니다. 기존 폼 구조를 유지해 변경 범위를 줄이겠습니다.”

**검증할 때:** “수정 전에는 A 초안이 B 요청에 들어가 테스트가 실패했습니다. 수정 후 이 경로와 서버 거절 후 재시도가 통과했습니다. 실제 서버의 권한 검사는 이 컴포넌트 테스트가 보장하지 않습니다.”

**시간이 부족할 때:** “계정 경계와 실패 복구는 수정했습니다. 집계 기간 경계는 재현만 했고 수정하지 못했습니다. 다음에는 KST 하루 구간의 시작·끝 테스트를 추가하겠습니다.”

### 종합 변형 문제 3개와 해설 방향

#### A. 금융 광고 성과 대시보드

기능: 계정 선택, 기간 조회, 캠페인 목록, 요약 카드, 정렬·페이지네이션.

해설 순서: 계정 데이터 격리 → 기간/집계 계약 → 목록 보존 → 전체 정렬 범위. 05·09·01·02·06의 코드를 조합합니다. 계정 A·B 동일 ID, 노출 규모가 다른 2행, 성과 누락, 자정 경계, 2페이지 데이터가 1페이지보다 큰 비용인 경우를 검증합니다.

기능: 상세 패널, 예산 저장, 심사 상태, 운영 토글, 선택 항목 일괄 중지.

해설 순서: 잘못된 대상 쓰기 차단 → 허용 상태 전환 → 저장 충돌/실패 복구 → 일괄 결과 처리. 10·04·03·08을 연결합니다. A→B 전환, 동료 version 갱신, 미승인 광고, 성공·거절·결과 불명의 혼합 응답을 검증합니다.

기능: 큰 테이블 검색, 조회 갱신, 보고서 생성, 완료 폴링, 필터 변경.

### 변형 문제의 답을 스스로 확인하기

**성과 누락을 서버가 0이라고 보장한다면?** 02의 미집계 표시 정책을 바꿀 수 있습니다. 다만 API 조회 실패는 여전히 실제 0과 다릅니다. 누락의 의미와 요청 실패를 분리해서 판단했는지가 핵심입니다.

**저장 중에도 사용자가 금액을 고칠 수 있다면?** 성공 응답은 제출한 금액의 저장 결과입니다. 제출 이후 작성한 새 초안까지 덮지 않도록 변경 여부를 추적해야 합니다. 저장 중 입력을 잠그던 코드의 전제가 바뀐 것입니다.

**보고서의 클릭 시점 데이터까지 고정해야 한다면?** 12의 조건 복사만으로 부족합니다. 서버가 그 시점의 데이터를 일관되게 읽을 수 있는 스냅샷이나 버전 계약이 필요합니다. 프론트에서 Date.now를 보낸다는 것만으로 과거 데이터가 복원되지는 않습니다.

**Worker를 넣어도 화면이 느리다면?** 계산이 아니라 DOM 생성·렌더가 병목일 수 있습니다. 전후 측정을 비교하고 데이터 전달 비용도 확인합니다. 도구를 추가했다는 사실을 개선의 증거로 삼지 않습니다.

### 외우는 대신 확인할 준비 기준

- 코드 없이 증상과 재현 조건을 설명할 수 있다.
- 고친 코드가 무엇을 보장하고 무엇을 보장하지 않는지 말할 수 있다.
- 요구사항이 하나 바뀌면 기존 해결법의 한계를 지적할 수 있다.
- 테스트를 구현 그대로 따라 쓰지 않고 기대 동작으로 작성할 수 있다.
- 확인하지 못한 사실을 숨기지 않고 다음 확인 방법을 설명할 수 있다.

추가 기반이 필요하면 JS Promise·클로저·참조, React 렌더·Effect·폼, TypeScript union·unknown, HTTP 상태·인증, 테스트 mock과 비동기 완료 제어를 다시 학습합니다. 9개 공통 이론과 12개 사례는 학습 출발점이며 면접의 모든 질문을 보장하지 않습니다.

### 네 가지 기준을 Ads 코드에 적용하기

공식 문서는 변경 용이성을 가독성·예측 가능성·응집도·결합도로 살펴봅니다. 기준끼리 충돌할 수 있으므로 모두를 무조건 최대화하는 규칙으로 사용하지 않습니다. 다음 표의 사례와 판단 질문은 이 교재의 적용 예입니다. [공식 기준](https://frontend-fundamentals.com/code-quality/code/)

| 기준 | 쉽게 말하면 | 이 교재에서 확인할 부분 |
| --- | --- | --- |
| 가독성 | 한 동작을 이해할 때 얼마나 많은 맥락을 따라가야 하는가 | 시작 버튼을 읽으면서 심사·권한·종료 조건을 파악할 수 있는가 |
| 예측 가능성 | 이름·입력·출력으로 실제 동작을 예상할 수 있는가 | 조회 함수가 몰래 선택 항목을 지우거나 저장 요청을 보내지 않는가 |
| 응집도 | 함께 바뀌어야 하는 규칙이 함께 관리되는가 | 예산 최솟값 변경 때 검증·안내·테스트가 함께 바뀌는가 |
| 결합도 | 한 기능의 변경이 무관한 기능에 얼마나 번지는가 | 보고서 조회 수정 때문에 예산 편집 코드도 수정해야 하는가 |

예를 들어 예산 최소 금액을 세 곳에 따로 쓰면 각 코드는 짧아도 하나만 바뀌어 정책이 불일치할 수 있습니다. 이때 도메인 규칙을 공유하면 함께 바꿀 부분을 모을 수 있습니다. 반면 모양이 같은 두 입력창이 서로 다른 승인 정책을 가졌다면 하나의 범용 폼으로 묶는 비용이 더 클 수 있습니다.

“Clean Code라서 분리했습니다”만으로는 근거가 부족합니다. **어떤 변경 시나리오에서 어느 파일·조건을 덜 확인하게 되는지**를 말하세요. 줄 수가 줄어도 중요한 정책이 여러 함수 뒤로 숨어 이해가 더 어려워질 수 있습니다.

### 선언적인 UI는 어떤 뜻인가

현재 상태에 따라 무엇을 보여줄지 코드 구조로 표현하는 방식입니다. 예를 들어 “저장 중이면 버튼을 막는다”를 DOM을 직접 찾아 조작하는 대신 상태와 JSX의 관계로 드러낼 수 있습니다.

아래는 현재 연습 문제의 정답이 아닌 독립적인 수업 발췌입니다. 저장 요청과 오류 처리 구현은 생략하고 표시 정책만 비교합니다.

```tsx
type SaveState =
  | { kind: 'idle' }
  | { kind: 'saving' }
  | { kind: 'failed'; message: string };

function SaveButton({
  state,
  onSave,
}: {
  state: SaveState;
  onSave: () => void;
}) {
  return (
    <div>
      <button disabled={state.kind === 'saving'} onClick={onSave}>
        {state.kind === 'saving' ? '저장 중…' : '예산 저장'}
      </button>
      {state.kind === 'failed' && <p role="alert">{state.message}</p>}
    </div>
  );
}
```

이 표현은 로딩·실패 메시지의 근거가 되는 상태를 드러냅니다. 하지만 중복 요청의 서버 처리, 저장 대상의 소속, 실패 후 초안 보존까지 보장하지는 않습니다. 선언적인 표현과 실제 동작의 안전성을 함께 검증해야 합니다.

조건을 함수로 옮기는 것도 이름이 의미를 전달할 때 유용합니다. `check()`보다 `getActivationDecision()`이 반환 목적을 설명하기 쉽습니다. 그 함수가 내부에서 광고를 시작해 버린다면 판정이라는 이름과 실제 동작이 어긋납니다. 부수 효과는 저장 명령처럼 분명한 흐름에 두는 것이 이 수업의 기준입니다.

### 커스텀 훅과 일반 함수의 경계

커스텀 훅은 React의 상태나 다른 Hook을 조합해 재사용하는 단위입니다. 훅을 호출한 곳들의 지역 state가 자동으로 하나로 공유되는 것은 아닙니다. 캐시나 외부 저장소를 쓰는 경우에는 그 저장소의 공유 규칙이 따로 있습니다.

| 후보 로직 | 우선 고려할 위치 | 이유 |
| --- | --- | --- |
| 클릭·노출로 CTR 계산 | 일반 순수 함수 | React 생명주기와 무관한 입력·출력 |
| 예산 문자열 검증 | 도메인 함수 | UI 없이도 같은 정책을 검증할 수 있음 |
| 계정별 성과 조회 | 조회 Hook | 조회 key·구독·재조회 상태를 함께 관리 |
| 초안·저장·충돌 안내 | 편집 전용 Hook 또는 컴포넌트 내부 | 같은 사용자 작업의 상태 전이를 함께 이해해야 함 |
| 모든 화면의 모든 동작 | 거대한 공용 Hook은 재검토 | 무관한 정책과 옵션이 서로 얽히기 쉬움 |

분리 전에는 세 가지를 확인합니다. 첫째, 무엇이 함께 바뀌는가. 둘째, 호출자가 몰라도 되는 상세가 무엇인가. 셋째, 분리 후 입력·결과·실패 계약이 더 명확해지는가. 재사용 횟수만으로 결정하지 않습니다. 한 번만 쓰더라도 복잡한 조회 정책을 감춰 화면 흐름을 명확하게 할 수 있습니다.

반례도 있습니다. 다섯 줄짜리 일회성 로직을 여러 파일로 흩뜨려야 읽을 수 있게 만들면 분리 비용이 더 클 수 있습니다. `useCampaignEverything({ mode, silent, autoSave, ... })`처럼 옵션 조합이 늘어나면 실제로 같은 책임인지 다시 봅니다.

토의 답변 예시:

> “계정·기간에 따른 조회 key와 재조회 상태가 함께 바뀌므로 조회 Hook으로 묶었습니다. CTR 계산은 React와 무관해 일반 함수로 남겼습니다. 저장 충돌은 다른 책임이므로 조회 Hook에서 처리하지 않습니다. 호출자는 조회 상태와 데이터의 의미를 알 수 있고, 계산은 별도로 테스트할 수 있습니다.”

## 14. Suspense·오류 처리·복구 경계 이해하기

### 용어를 먼저 구분하기

Suspense는 지원되는 자식의 로딩 동안 fallback을 보여주는 경계입니다. Effect 안의 fetch나 이벤트 핸들러의 Promise를 자동으로 감지하는 기능은 아닙니다. Suspense를 지원하는 데이터 조회 방식과 함께 사용해야 합니다. [React Suspense](https://react.dev/reference/react/Suspense)

Error Boundary는 자식 렌더링 오류를 대체 화면으로 처리하는 경계입니다. 일반적인 클릭 핸들러나 비동기 콜백에서 발생한 오류를 자동으로 모두 처리하지 않습니다. 저장 실패는 해당 이벤트·mutation의 처리 흐름에서 다뤄야 합니다. [React Error Boundary](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)

사용자가 언급한 ErrorHandler는 React의 표준 컴포넌트 이름이 아닙니다. 프로젝트가 만든 오류 분류 함수나 UI일 수 있으므로 구현과 역할을 확인합니다. “에러를 잡는다”를 오류 감지, 분류, 사용자 표시, 재시도, 기록으로 나누어 설명하세요.

### 경계의 크기는 사용자 경험의 결정이다

캠페인 이름 목록은 성공했지만 성과 조회만 실패했다고 가정합니다. 페이지 전체를 하나의 오류 화면으로 바꾸면 목록 탐색도 막힙니다. 이 제품에서 목록을 계속 이용해야 한다면 성과 영역만 실패와 재시도를 표시하도록 경계를 잡습니다.

반대로 함께 있어야 의미 있는 데이터라면 일부만 보여주는 것이 사용자 오판을 만들 수 있습니다. 별도 경계가 많다고 항상 좋은 것이 아닙니다. **사용자가 어떤 영역을 함께 기다려야 하고, 어느 영역은 실패해도 사용할 수 있어야 하는지**부터 정합니다.

다음은 컴포넌트 관계를 보여주는 설계도입니다. `MetricsErrorBoundary`는 별도 구현이 필요한 앱 컴포넌트이고 `Metrics`는 Suspense 지원 조회를 사용한다는 전제입니다.

```tsx
<CampaignWorkspace>
  <CampaignList />
  <MetricsErrorBoundary>
    <Suspense fallback={<MetricsLoading />}>
      <Metrics />
    </Suspense>
  </MetricsErrorBoundary>
</CampaignWorkspace>
```

이 구조만으로 재시도가 구현되는 것은 아닙니다. 오류 UI를 리셋하고 조회 계층이 재요청하도록 연결해야 합니다. 계정 변경 시 이전 오류·응답의 소속도 정리해야 합니다.

### TanStack Query를 쓴다면

`useSuspenseQuery`는 성공 데이터를 사용하는 화면과 로딩·오류 경계를 나누는 데 사용할 수 있습니다. 오류 경계의 재시도에는 `QueryErrorResetBoundary` 또는 관련 reset 기능을 연결합니다. 캐시 데이터가 있으면 모든 재조회 오류가 자동으로 경계로 전달되는 것은 아니므로 기존 결과 유지와 오류 표시 정책도 확인합니다. [TanStack Query Suspense 가이드](https://tanstack.com/query/latest/docs/framework/react/guides/suspense)

저장 오류를 전부 페이지 오류로 던지는 것도 정답은 아닙니다. 입력 오류나 409 충돌은 폼 옆에서 설명하고 초안을 유지하는 편이 요구사항에 맞을 수 있습니다. 이 저장소의 실제 의존성과 API를 확인한 뒤 구현하며, 예시를 위해 새 라이브러리를 무조건 추가하지 않습니다.

| 상황 | 이 수업에서 우선 검토할 처리 | 확인할 결과 |
| --- | --- | --- |
| 최초 성과 로딩 | 성과 영역 로딩 표시 | 캠페인 목록은 계속 사용 가능 |
| 최초 성과 조회 실패 | 영역 오류·재시도 | 성공한 다른 영역 보존 |
| 기존 성과의 갱신 실패 | 기존값과 갱신 실패 안내 | 오래된 값임을 오해하지 않음 |
| 예산 입력 오류 | 입력창 가까이 안내 | 요청 전 유효성 확인 |
| 저장 409 | 최신값 확인과 초안 보존 | 자동 덮어쓰기 방지 |
| 저장 타임아웃 | 결과 불명 안내와 확인 | 실패로 단정하고 중복 저장하지 않음 |

토의에서는 “Suspense를 안 쓰고 상태 분기로 유지하면 어떤 장단점이 있나?”도 다룹니다. 기존 구조가 명료하고 범위가 작다면 명시적인 로딩·오류 분기도 타당합니다. 라이브 코딩에서 패턴 교체가 핵심 버그 수정을 방해하면 수정 범위를 줄이는 판단을 설명합니다.

## 15. 추가 모의 과제와 시간제한 연습

### 공개 과제 카드와 실전 문제의 차이

아래는 학습용 과제 요구사항입니다. 아직 새로운 실행 앱이나 채점용 숨은 결함을 만든 것은 아닙니다. “FF-A 실전 문제 만들어줘”처럼 요청하면 저장소의 생성 절차로 독립적인 before·working·공개 테스트를 만들고, 숨은 결함과 개선안은 비공개 영역에만 둡니다. 지금 공개된 해설을 읽었다는 이유로 기존 문제의 정답을 열지 않습니다.

현재 Level 2 진도는 유지합니다. 처음에는 각 카드의 한 가지 흐름만 2~4개 작업 파일·30~40분으로 연습할 수 있습니다. 45분은 사용자가 선택하는 확장 연습이고, 60분 Level 3 종합형을 선택하면 8~12개 연결된 작업 파일·4~6개 핵심 결함 기준을 적용합니다. 자동으로 난이도를 올리지 않습니다.

### FF-A. 캠페인 목록과 성과 영역 — 45분 확장형

**상황:** 운영자는 광고 계정과 기간을 선택해 캠페인 목록과 성과를 봅니다. 목록 조회와 성과 조회는 별도 API입니다.

**요구사항:**

- 계정이 바뀌면 선택 항목과 표시 데이터가 새 계정에 속해야 합니다.
- 목록이 먼저 준비되면 목록을 사용할 수 있어야 합니다.
- 성과만 실패하면 목록을 유지하고 성과 영역에서 재시도할 수 있어야 합니다.
- 성과 응답에 없는 캠페인은 목록에 유지하고 미집계로 표시합니다.
- 새 기간의 결과가 표시된 뒤 이전 기간 응답으로 되돌아가지 않아야 합니다.
- 조회·표시·계산의 책임을 설명하고, 필요한 범위에서 구조를 개선합니다.

**공개 서버 계약:** 계정 내 캠페인 ID는 유일하고 성과 누락은 미집계입니다. 읽기 API는 반복 요청할 수 있습니다. 지연·실패를 목 환경에서 재현할 수 있습니다.

**검증 시나리오:** 목록 성공/성과 실패, 성과 재시도 성공, 기간 빠른 변경, 계정 A·B에 같은 ID가 있는 경우.

**연습할 설명:** “목록과 성과의 실패 경계를 왜 이 위치에 뒀는가?”, “조회 Hook을 분리해 호출자가 몰라도 되는 것은 무엇인가?” 02·05·07과 13·14를 연결합니다. 특정 Hook이나 Suspense 사용은 필수 조건이 아닙니다.

### FF-B. 예산 편집과 운영 상태 변경 — 45분 확장형

**상황:** 운영자는 상세 패널에서 예산을 수정하고 광고를 시작하거나 중지합니다.

**요구사항:**

- 예산은 10,000~10,000,000원 정수이며 저장 거절 시 초안을 유지합니다.
- 미저장 초안이 있을 때 다른 광고로 이동하면 취소 또는 폐기 후 이동을 선택합니다.
- 저장 중 입력과 항목 이동은 잠그는 정책으로 시작합니다.
- 승인된 PAUSED 광고만 편집 권한이 있을 때 시작할 수 있습니다.
- 저장 충돌과 일반 통신 오류를 구분해 안내합니다.
- 정책 판정, 서버 변경 명령, 화면 표시의 경계를 설명합니다.

**공개 서버 계약:** 버전 조건이 맞지 않으면 409이며 변경하지 않습니다. 성공은 새 버전과 확정값을 반환합니다. 서버도 계정 권한과 상태 전환을 검사합니다.

**검증 시나리오:** 정상 저장, 경계 금액, 충돌 후 초안 유지, 이동 취소, 시작 불가 이유, 거절 뒤 다시 조작.

**연습할 설명:** “입력 검증을 Hook 대신 함수로 둔 이유는?”, “시작·중지를 하나의 범용 토글로 묶을 때 어떤 계약이 숨는가?” 03·04·10을 연결합니다.

### FF-C. 보고서 생성과 작업 상태 — 60분 종합형

**상황:** 운영자는 필터에 맞는 전체 광고 보고서를 생성하고 진행 상태를 확인합니다.

**요구사항:**

- 현재 페이지가 아니라 필터 전체가 작업 대상입니다.
- 생성 시점의 계정·기간·필터를 고정하고 작업 라벨에도 같은 조건을 씁니다.
- 같은 화면에서는 한 번에 한 생성 요청만 시작합니다.
- 서버 작업 상태는 queued·running·done·failed이고 done에서 다운로드할 수 있습니다.
- 상태 조회가 실패한 것과 작업 자체가 실패한 것을 구분합니다.
- 완료·실패·화면 종료 시 반복 조회를 정리하고 이전 계정 응답을 새 화면에 적용하지 않습니다.
- 조회, 작업 생성, 작업 상태, 파일 접근의 책임과 복구 흐름을 설명합니다.

**공개 서버 계약:** 생성은 job ID를 반환하며 생성 재시도의 멱등성은 보장하지 않습니다. 작업 상태 조회는 반복할 수 있습니다. 다운로드 권한은 서버가 검사합니다. 조건 스냅샷은 고정하지만 클릭 시점의 데이터 내용까지 보장하는 계약은 아닙니다.

**검증 시나리오:** 120건 중 20건 페이지, 생성 후 필터 변경, 폴링 통신 실패 후 복구, done·failed 이후 추가 조회 없음, 계정 변경 중 응답 도착.

**연습할 설명:** “범용 비동기 Hook 하나에 모두 넣지 않은 이유는?”, “생성 요청과 상태 조회의 재시도를 왜 다르게 처리하는가?” 07·12와 13·14를 연결합니다.

### 시간 운영과 화면 공유

| 단계 | 45분 | 60분 | 할 일 |
| --- | --- | --- | --- |
| 이해 | 0~7분 | 0~10분 | 전체 역할·입출력·동작 설명, 필요한 계약 확인 |
| 재현·계획 | 7~13분 | 10~18분 | 사용자 영향과 우선순위, 실패 테스트 |
| 수정 | 13~30분 | 18~42분 | 핵심 결함 수정, 필요한 구조 개선 |
| 검증 | 30~39분 | 42~53분 | 정상·실패·재시도·경계·회귀 |
| 설명·토의 | 39~45분 | 53~60분 | 선택 근거, 대안, 미완료 항목과 꼬리질문 |

이 배분은 연습용입니다. 면접 시작을 요청했을 때 제한 시간과 시작 시각을 정하고, 사전 읽기 시간과 구분합니다. 시간 종료 시 완료 상태와 미검증 항목을 먼저 말한 뒤 리뷰로 전환합니다.

화면 공유는 사용자가 가능한 도구로 별도 시작합니다. AI가 현재 화면을 볼 수 있는지 확인하고, 볼 수 없다면 변경 diff·코드·실행 결과를 바탕으로 진행합니다. 화면을 보지 않고 클릭 동작이나 테스트 통과를 관찰했다고 말하지 않습니다. 실제 면접의 AI·검색 허용 여부는 회사 안내를 따릅니다.

## 16. 코드 설명·꼬리질문·피드백

### 시작 질문

> 코드 전체의 역할과 입력·출력, 주요 동작 흐름을 설명해주세요. 이어서 발견한 문제점과 사용자 영향, 수정 우선순위와 해결 방안, 검증 방법까지 한 번에 말씀해주세요.

첫 설명이 끝나기 전에는 질문을 쪼개거나 숨은 문제를 알려주지 않습니다. 이후에는 지원자가 실제로 언급한 선택을 기준으로 아래 질문에서 필요한 것만 고릅니다. 질문 목록을 차례로 모두 소진하는 방식은 사용하지 않습니다.

### 답변에 따라 고르는 질문과 학습 해설

| 지원자가 설명한 선택 | 이어서 물을 질문 | 해설에서 확인할 근거 |
| --- | --- | --- |
| 커스텀 훅으로 분리 | 호출자가 더 이상 몰라도 되는 상세는 무엇이며, 순수 함수만으로는 부족했나요? | React 상태·구독과 순수 계산의 구분, 명확한 계약 |
| 공통화 | 한 화면의 정책만 바뀌면 다른 화면에 어떤 수정이 필요한가요? | 같은 변경 이유인지, 옵션·분기 비용이 늘어나는지 |
| 중복 유지 | 어떤 변화가 생기면 공유해야 한다고 판단하나요? | 중복된 정책의 불일치 위험과 독립 변경 가능성 |
| 선언적 UI | 상태를 이렇게 나눠도 표현 가능한 잘못된 조합이 있나요? | 상태 모델의 의미, 동작 검증과 표시의 구분 |
| Suspense 도입 | 무엇이 실제로 suspend하며, 이 영역을 함께 기다려야 하는 이유는 무엇인가요? | 조회 방식과 사용자에게 보이는 로딩 단위 |
| 오류 경계 도입 | 저장 버튼의 비동기 실패도 이 경계가 자동으로 처리하나요? | 이벤트 오류와 렌더 오류의 구분 |
| 재시도 제공 | UI를 닫는 것 외에 어떤 조회 상태를 리셋하며, 중복 적용 위험은 없나요? | reset·재조회 연결, 조회와 변경 명령의 차이 |
| 성능 개선 | 같은 입력에서 전후 무엇을 측정했고 결과가 같다는 것은 어떻게 확인했나요? | 병목 증거와 정확성 회귀 |
| 최소 수정 | 다음 요구사항 하나가 바뀌면 어느 부분을 수정해야 하나요? | 변경 범위와 아직 남은 결합 |
| 테스트 추가 | 수정 전 실패가 설정 오류가 아니라 의도한 사용자 결함 때문임을 어떻게 알았나요? | 관찰값·재현 순서·실패 이유 |

위 오른쪽 열은 이론 학습용 해설입니다. 실전 면접에서는 답변 전에 읽어주거나 특정 해결책으로 유도하지 않습니다.

### 틀렸거나 모르겠다고 했을 때의 피드백 예시

**답변:** “커스텀 훅으로 빼면 여러 컴포넌트에서 state를 공유합니다.”

**교정:** “로직을 재사용한다는 부분은 맞지만, Hook 내부 useState는 호출마다 별도입니다. 공유가 필요하면 상위 상태나 외부 저장소·쿼리 캐시 같은 명시적인 공유 경계를 정해야 합니다.”

**이어갈 질문:** “지금 초안은 한 편집기 안에만 있어도 되나요, 다른 화면에도 유지되어야 하나요? 그 요구에 맞는 소유 위치를 설명해주세요.”

**답변:** “Suspense가 모든 API 오류를 잡아서 처리합니다.”

**교정:** “Suspense는 지원되는 로딩을 다루고 오류 표시는 Error Boundary 등의 역할입니다. 일반 이벤트의 저장 실패도 자동으로 처리되는 것은 아닙니다. 조회와 저장의 실패 전달 경로를 구분해야 합니다.”

**이어갈 질문:** “성과 조회는 실패해도 목록을 유지하고, 저장 실패에서는 초안을 유지해야 합니다. 각각 어디에 오류를 보여주겠습니까?”

**모르겠다는 답변:** 같은 질문을 말만 바꾸어 반복하지 않습니다. 개념·적용 조건·반례를 설명하고 독립적인 작은 예제로 확인한 뒤 다음으로 넘어갑니다. 원래 실전 문제의 완성 코드와 숨은 결함은 공개하지 않습니다.

### 평가와 기록

기존 100점 배점은 유지합니다. 발견 정확도 20, 우선순위 15, 동작 수정 25, 코드 품질 20, 테스트 10, 의사소통 10입니다. 네 가지 품질 기준은 코드 품질과 의사소통의 근거를 구체화하는 관점이며 별도 가산점을 중복 부여하지 않습니다.

Suspense를 사용했거나 Hook 개수가 늘었다는 이유로 점수를 주지 않습니다. 타당한 대안을 오답으로 취급하지 않고 요구사항·변경 비용·검증으로 평가합니다. review에는 실제 질문과 답변 요지, 정확한 부분, 교정한 개념, 선택의 장단점, 다음 변형 연습 한 가지를 남깁니다. 기존 비공개 자료 처리 규칙을 그대로 따릅니다.
