# 11. 검색할 때 대량 테이블이 멈춘다

## 요구사항과 Before

학습용 데이터는 최대 20,000개 소재이며 ID는 유일합니다. 이름과 비용을 결합하고 검색·정렬합니다. 숫자는 연습용 상한이며 토스의 실제 데이터 규모가 아닙니다.

```ts
const rows = creatives.map((creative) => ({
  ...creative,
  spendWon: metrics.find((metric) => metric.id === creative.id)?.spendWon ?? null,
}));
```

## 재현과 우선순위

큰 데이터에서 타이핑 지연을 측정합니다. 매 입력마다 n개 항목에서 m개 성과를 찾으면 O(n×m) 비용입니다. 하지만 네트워크 지연·필터 계산·React 렌더·브라우저 레이아웃 중 실제로 무엇이 느린지 먼저 측정해야 합니다.

작업 자체가 멈출 정도면 성능도 높은 우선순위입니다. 데이터가 틀리거나 잘못된 광고 변경이 동시에 있다면 정확성 보호를 먼저 하고 성능을 이어서 해결하는 식으로 범위를 협의합니다.

## After

```ts
const byId = new Map(metrics.map((metric) => [metric.id, metric]));
const rows = creatives.map((creative) => ({
  ...creative,
  spendWon: byId.get(creative.id)?.spendWon ?? null,
}));
```

색인을 한 번 만들면 일반적인 Map 조회 비용을 가정해 전체 결합을 O(n+m) 수준으로 줄입니다. 입력 데이터가 바뀌지 않았다면 이 결합을 매 키 입력마다 다시 할 필요도 없습니다. 결과가 같은지 테스트하고 측정 전후 시간을 비교합니다.

## 해결책마다 다른 대상

| 방법                   | 줄이는 비용           | 해결하지 않는 것              |
| ---------------------- | --------------------- | ----------------------------- |
| 색인·한 번만 합계 계산 | 반복 계산             | DOM 수                        |
| useMemo                | 같은 입력의 재계산    | 첫 계산·새 입력 계산          |
| 가상화                 | 화면 밖 DOM 렌더      | 전체 정렬 계산                |
| debounce               | 처리 빈도             | 한 번의 무거운 계산·응답 순서 |
| Worker                 | 메인 스레드 계산 부담 | 데이터 전달 비용·전체 계산량  |
| 서버 조회              | 브라우저 메모리·계산  | 네트워크 대기·서버 부하       |

Worker로 옮겨도 결과 순서가 바뀔 수 있습니다. 메시지에 requestId를 붙여 최신 요청 결과만 적용합니다. 데이터 복제·전달 비용, 메모리 상한, Worker 실패 복구도 설계해야 합니다. 전체 다운로드는 상한과 권한이 확인된 경우에만 선택합니다.

## 검증

같은 데이터·장치·조건에서 최초 로딩과 반복 검색 시간을 나누어 측정합니다. 작은 데이터에서 빠르다는 사실만으로 개선됐다고 결론 내리지 않습니다. 정렬 결과·누락 항목·안정적인 행 ID가 유지되는지도 확인합니다.

## 면접에서 말하기

> “먼저 계산과 렌더 시간을 분리해 측정하겠습니다. 반복 find가 병목이면 색인을 만들어 변경 범위를 줄이고, DOM이 병목일 때 가상화를 검토하겠습니다. Worker를 넣는 것 자체를 목표로 삼지는 않겠습니다.”

**꼬리질문:** 서버 처리와 클라이언트 처리 중 정답은?

**해설:** 데이터 상한, 응답 크기, 변화 빈도, 보안 경계, 사용자 탐색 패턴에 따라 선택합니다. 한 제품의 선택을 모든 운영툴에 적용할 수 없습니다.
