# 12. 내보낸 보고서가 화면 조건과 다르다

## 개념부터 풀어보기

화면의 페이지는 전체 결과 중 일부입니다. 내보내기 요구사항이 ‘필터에 맞는 전체’라면 현재 페이지 배열만 CSV로 만들 수 없습니다. CSV는 표의 행과 열을 텍스트로 저장하는 형식입니다. 파일이 만들어졌다는 사실만으로 내용이 완전하다고 판단하지 않습니다.

job은 서버가 오래 걸리는 작업을 식별·추적하는 단위입니다. 생성 응답의 job ID는 작업 접수를 뜻하며 파일 완성을 뜻하지 않을 수 있습니다. 이 수업에서는 그 ID로 상태를 반복 조회하는 폴링을 사용합니다.


## 요구사항과 Before

현재 페이지가 아니라 현재 필터에 맞는 전체 결과를 내보냅니다. 내보내기 버튼을 누른 시점의 계정·기간·조건을 작업에 고정합니다. 서버 job ID로 완료를 확인합니다.

```ts
downloadCsv(currentPageRows);
```

## 재현과 우선순위

조건에 맞는 광고가 120개인데 첫 페이지 20개만 내려받습니다. 사용자는 전체 보고서라고 생각할 수 있습니다. 외부 보고와 수치 비교에 사용되는 기능이라면 데이터 완전성 문제입니다. 서버가 전체 결과를 내보내는 API를 제공하는지 먼저 확인합니다.

## After: 전체 결과와 조건을 서버 작업에 고정

```ts
// page를 내보내기 계약에서 제외. 조건은 원시값으로 복사
const snapshot = {
  accountId,
  from: filters.from,
  to: filters.to,
  status: filters.status,
  keyword: filters.keyword,
};
const job = await api.createExport(snapshot);
setExportJob({ id: job.id, snapshot });
```

화면 필터가 바뀌어도 이미 시작한 작업의 라벨·파일명은 snapshot 기준입니다. 응답 시점의 최신 필터로 파일명을 만들지 않습니다. “버튼 시점 조건”을 고정해도 그 사이 서버 데이터 자체가 바뀔 수 있습니다. 정확한 데이터 스냅샷이 필요하면 서버가 기준 시각·버전까지 보장해야 합니다.

폴링은 같은 요청이 끝나기 전에 다음 요청이 겹치지 않게 합니다. done·failed에서 중지하고 unmount·계정 변경에서도 정리합니다. 알려지지 않은 status는 영원히 로딩으로 두지 말고 응답 계약 오류로 처리합니다. 다운로드 권한은 서버가 검사합니다.

## 두 종류의 스냅샷을 구분하기

| 구분 | 고정하는 것 | 예시 |
| --- | --- | --- |
| 조건 스냅샷 | 클릭 당시 계정·기간·필터 | 9월 27일 ACTIVE 광고 전체 |
| 데이터 스냅샷 | 특정 시점의 실제 데이터 내용 | 10:00에 확정된 성과와 상태 |

코드의 snapshot은 첫 번째입니다. 10:00에 작업을 요청하고 10:01에 서버가 조회하는 동안 광고 상태가 바뀌면 대상이나 성과가 달라질 수 있습니다. 버튼 시점 데이터까지 고정해야 한다면 서버가 조회 버전이나 일관된 기준 시각을 보장해야 합니다.

조건 값을 각각 복사하는 것은 이후 filters 변경이 기존 작업에 영향을 주지 않게 하기 위함입니다. 이 예시의 필드는 문자열 같은 원시값입니다. 배열·중첩 객체 필터를 추가하면 참조 공유와 변경 가능성을 따로 확인해야 합니다.

page를 뺀 이유는 현재 페이지만 내보내는 작업이 아니기 때문입니다. 내보내기 순서까지 화면과 같아야 한다면 정렬 조건도 고정해 전달해야 합니다. 표시할 열이나 통화도 결과에 영향을 준다면 작업 계약에 포함합니다.

## 폴링의 시작과 끝

1. 클릭 당시 조건으로 작업을 생성합니다.
2. 반환된 job ID와 그 조건을 함께 저장합니다.
3. 작업이 진행 중이면 상태를 조회합니다.
4. 조회가 끝난 뒤 일정 간격 후 다음 조회를 예약합니다.
5. done이면 다운로드 단계로, failed이면 실패 안내로 이동하고 반복을 멈춥니다.

일정 간격마다 무조건 요청하는 방식은 느린 응답에서 요청이 겹칠 수 있습니다. 화면을 닫거나 계정을 바꾸면 타이머를 정리하고 이미 진행 중인 응답도 이전 화면에 적용되지 않게 해야 합니다. 타이머 제거만으로 이미 보낸 요청의 응답이 없어지지는 않습니다.

조회 중단이 서버 파일 생성 취소를 뜻하지는 않습니다. 취소가 필요하면 서버 취소 API가 별도로 있어야 합니다. 폴링 통신 실패와 job 자체의 failed도 다릅니다. 통신 실패 시 서버 작업은 계속될 수 있으므로 제한된 재조회·재시도 정책을 정의합니다.

이 발췌는 한 번에 한 작업만 생성하는 화면을 전제로 합니다. 여러 작업을 허용하면 하나의 setExportJob 값으로 덮어쓰기보다 job별 상태를 관리해야 합니다. 늦은 생성 응답도 제출 당시 계정에 속하도록 처리합니다.

검증에서는 화면 라벨만 보지 말고 실제 파일의 행 수·조건·집계 기준 시각을 확인합니다. 다운로드 URL을 안다고 권한을 우회할 수 없어야 하므로 파일 접근 시 서버 권한도 검사해야 합니다.

## 검증

전체 120개가 대상인지, 페이지 파라미터가 전달되지 않는지, 시작 후 필터를 바꿔도 job의 조건이 유지되는지 확인합니다. 완료·실패 후 더 이상 폴링하지 않는지, 이전 계정의 job 응답이 새 계정 화면에 연결되지 않는지 검사합니다. 실제 파일 행 수와 집계 기준 시각도 별도 통합 검증 대상입니다.

## 면접에서 말하기

> “화면 페이지 데이터는 전체 내보내기 범위와 다릅니다. 서버 작업에 클릭 시점 조건을 고정하고 작업 상태와 화면 조회 상태를 분리하겠습니다. 파일 내용의 기준 시각까지 일치해야 하는지는 추가로 확인하겠습니다.”

**꼬리질문:** 버튼만 disabled면 끝인가?

**해설:** 중복 클릭만 줄일 뿐 조건 불일치·전체 범위·계정 권한·폴링 정리는 해결되지 않습니다. 작업의 입력, 소유 계정, 수명과 결과 계약을 함께 정의해야 합니다.
