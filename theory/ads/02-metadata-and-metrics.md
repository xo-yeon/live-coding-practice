# 02. 성과가 없는 캠페인이 목록에서 사라진다

## 개념부터 풀어보기

캠페인 메타데이터는 ID·이름·운영 상태처럼 ‘어떤 광고인가’를 설명합니다. 성과는 노출·클릭·비용처럼 ‘얼마나 집행되었는가’를 설명합니다. 새 캠페인은 이름과 ID가 있어도 아직 성과가 없을 수 있습니다.

이 화면의 목적은 캠페인 관리입니다. 따라서 목록에 나올 대상은 캠페인 API가 결정하고 성과는 나중에 붙입니다. 이것을 ‘캠페인을 기준으로 결합한다’고 표현합니다.


## 요구사항과 Before

가상 대출 광고 운영 화면에는 오늘 생성한 캠페인도 보여야 합니다. 캠페인 목록과 성과 API는 별개이며 이 수업에서 성과 행 누락은 **미집계**를 뜻합니다. 행이 존재하고 노출이 0인 경우만 확정된 0으로 표시합니다.

```ts
const rows = metrics.map((metric) => ({
  ...campaigns.find((campaign) => campaign.id === metric.campaignId),
  ...metric,
}));
```

## 재현과 우선순위

캠페인은 A·B 두 개이고 성과 응답에는 A만 넣습니다. B가 화면에서 사라져 생성 실패로 오해할 수 있습니다. 신규 캠페인 확인이 핵심 운영 흐름이라면 먼저 고칠 동작 문제입니다.

## After

```ts
const byId = new Map(metrics.map((metric) => [metric.campaignId, metric]));
const rows = campaigns.map((campaign) => ({
  ...campaign,
  metric: byId.get(campaign.id) ?? null,
}));
```

목록의 기준은 캠페인 원본이고 성과는 부가 정보입니다. 메타데이터를 유지하면서 성과만 없다고 표현합니다. `null`을 임의로 0으로 바꾸지 않습니다. 다른 API에서 누락을 0으로 보장한다면 그 계약에 한해서 0을 채울 수 있습니다.

조회 실패·아직 로딩·성공했지만 행 없음도 구분합니다. 모든 누락을 `?? 0`으로 처리하면 장애까지 정상적인 0 실적으로 표시할 수 있습니다. 유일 ID를 보장하지 않는 응답이면 Map 생성 전에 중복 정책도 필요합니다.

## Before와 After를 따라가기

Before의 `metrics.map`은 성과가 있는 행만 순회합니다. 성과에 B가 없으면 B를 만들 기회 자체가 없습니다. After는 `campaigns.map`으로 A·B를 모두 만들고, Map에서 해당 성과를 찾습니다. Map은 `캠페인 ID → 성과 객체`를 저장하는 조회표입니다.

성과를 `metric` 필드 안에 넣으면 캠페인과 성과에 같은 이름의 필드가 있어도 서로 덮어쓰지 않습니다. `?? null`은 찾은 성과가 없을 때만 null을 채웁니다.

| 상태 | 의미 | 화면 |
| --- | --- | --- |
| 조회 중 | 응답이 아직 없음 | 성과 영역 로딩 |
| 성공, 행 있음, 값 0 | 서버가 0으로 집계함 | 0 |
| 성공, 해당 행 없음 | 이 수업의 계약상 미집계 | 미집계 |
| 조회 실패 | 성과를 알 수 없음 | 오류와 재시도 |

위 결합 함수는 **성과 API가 성공한 다음의 변환**입니다. 로딩·실패까지 null로 바꾸는 함수가 아닙니다. 조회 상태를 별도로 관리해야 장애를 ‘실적 없음’으로 오해하지 않습니다.

같은 ID가 여러 번 들어오면 Map은 나중 값을 남깁니다. 일별 성과 여러 행이라면 합산이 필요할 수 있고, 잘못된 중복이면 오류로 다뤄야 합니다. ‘ID가 유일하다’는 전제가 없는 곳에 그대로 적용하지 않습니다.

작은 목록을 클라이언트에서 합치는 것은 합리적일 수 있습니다. 그러나 캠페인 100개 중 20개와 성과 100개 중 다른 20개만 가져왔다면 두 응답을 합쳐도 전체 목록은 되지 않습니다. 서버 결합 여부보다 먼저 조회 범위를 확인합니다.

## 검증

A만 성과가 있는 상황에서도 A·B 두 행이 보여야 합니다. A의 노출 0은 `0`, B는 `미집계`로 표현합니다. 성과 API 실패 시 캠페인 목록은 유지하고 성과 영역에 오류·재시도를 표시하는 것이 이 수업의 정책입니다.

## 면접에서 말하기

> “성과 응답을 목록의 기준으로 사용해 미집계 캠페인이 빠집니다. 캠페인 목록을 기준으로 결합하고, 조회 실패와 미집계를 0과 구분하겠습니다.”

**꼬리질문:** 프론트에서 목록을 합치면 항상 좋은가?

**해설:** 데이터 상한, 응답 크기, 서버 조인 지원 여부에 따라 다릅니다. 여러 페이지 중 일부만 받아 합치면 완전한 목록이 되지 않습니다. 계약을 확인한 작은 수정과 전체 조회 구조 변경을 구분해야 합니다.
