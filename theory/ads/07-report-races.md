# 07. 보고 기간을 빠르게 바꾸면 오래된 성과가 표시된다

## 개념부터 풀어보기

응답 순서 경쟁은 ‘요청을 보낸 순서’와 ‘응답이 도착한 순서’가 달라 생깁니다. A를 먼저 요청했다고 A 응답이 먼저 오는 것은 아닙니다. 현재 화면이 B 기간이면 나중에 도착한 A 응답은 더 이상 화면을 바꿀 자격이 없습니다. 이 자격을 여기서는 요청의 소유권이라고 부릅니다.

| 시점 | 사건 | 기대 화면 |
| --- | --- | --- |
| 0ms | A 기간 조회 시작 | A 로딩 |
| 10ms | B 기간으로 변경 | B 로딩 |
| 110ms | B 응답 도착 | B 결과 |
| 800ms | A 응답 도착 | 계속 B 결과 |

Before는 모든 요청이 `setReport`를 실행하므로 마지막에 도착한 A가 B를 덮습니다. A의 오래된 실패 응답이 B의 성공 화면을 오류로 바꾸는 경우도 같은 문제입니다.


## 요구사항과 Before

보고 기간 A 요청은 800ms, B 요청은 100ms 걸립니다. 현재 선택 기간의 데이터만 표시하며 갱신 실패 시 마지막 성공 결과를 보여주더라도 기준 기간과 실패 사실을 명시해야 합니다.

```tsx
useEffect(() => {
  api.report(period).then(setReport);
}, [period]);
```

## 재현과 우선순위

A 직후 B를 선택하고 B→A 순서로 완료시킵니다. 제목은 B인데 숫자는 A가 되면 보고 해석이 틀어집니다. 색상이나 로딩 애니메이션보다 결과의 소속부터 고칩니다.

## After: 요청 key와 데이터 key를 연결

아래는 queryKey 문자열이 계정·기간·필터를 정규화해 식별하며 `api.report`가 이를 인자로 받는다고 가정한 Hook 발췌입니다.

```tsx
useEffect(() => {
  let active = true;
  setView({ key: queryKey, status: 'loading' });
  api.report(queryKey).then(
    (data) => {
      if (active) setView({ key: queryKey, status: 'success', data });
    },
    () => {
      if (active) setView({ key: queryKey, status: 'error' });
    },
  );
  return () => {
    active = false;
  };
}, [queryKey]);
const visible = view.key === queryKey ? view : { key: queryKey, status: 'loading' };
```

이 작은 수정에서는 기간 변경 시 이전 결과를 숨깁니다. Effect 실행 전 렌더에서도 key가 다른 데이터를 표시하지 않습니다. 공용 boolean ref를 새 요청마다 true로 바꾸면 이전 요청도 다시 자격을 얻을 수 있어, 각 Effect의 지역 변수를 씁니다.

같은 기간 재조회 중 기존 결과를 유지하려면 마지막 성공 데이터와 갱신 상태를 분리합니다. “집계 기준 시각”, “갱신 실패, 이전 결과 표시”를 함께 보여줍니다. 재조회 실패를 0 실적으로 바꾸거나 빈 결과라고 표시하지 않습니다.

## After 코드를 한 줄씩 연결하기

`queryKey`는 계정·기간·필터를 합쳐 ‘어떤 결과인가’를 식별하는 문자열입니다. 충돌 없이 일관된 방식으로 만들어야 합니다. 각 Effect 실행은 자신만의 `active` 변수를 만듭니다. 조건 변경이나 unmount 때 cleanup이 이전 실행의 active를 false로 바꾸어, 그 실행의 성공·실패 응답을 모두 무시합니다.

하나의 공용 ref를 매번 true로 되돌리면 이전 응답도 같은 true를 읽을 수 있습니다. 지역 변수는 요청별로 서로 다른 변수를 참조하므로 이전 실행만 비활성화할 수 있습니다. 이처럼 비동기 함수가 자신이 만들어질 때의 변수를 계속 참조하는 성질을 클로저라고 합니다.

`view.key === queryKey` 비교는 별도 역할을 합니다. 조건 변경 후 새 Effect가 실행되기 전 렌더에서도 A 데이터를 B 제목 아래 보여주지 않게 합니다. cleanup으로 늦은 응답을 무시하는 것과 현재 렌더에서 데이터의 소속을 확인하는 것을 함께 적용한 것입니다. [React useEffect 문서](https://react.dev/reference/react/useEffect)

## 같은 조건 재조회는 별도로 생각하기

이 발췌는 key 변경에 따른 조회를 보여줍니다. 같은 key에서 ‘재시도’를 눌러 다시 실행하려면 별도 재조회 트리거나 조회 라이브러리가 필요합니다. 같은 key의 요청 여러 개가 겹칠 수 있다면 실행 번호로 최신 실행을 식별해야 합니다. key만 같다고 모든 응답이 최신인 것은 아닙니다.

이전 성공 결과를 유지하는 제품에서는 데이터와 갱신 상태를 나눕니다. ‘9월 27일 성과, 10:00 집계 / 10:05 갱신 실패, 이전 결과 표시’처럼 숫자의 기준을 설명합니다. 여기서 오래된 데이터는 마지막 성공값이지 0이 아닙니다.

요청 취소는 낭비를 줄이는 수단이고, 응답 무시는 잘못된 화면 변경을 막는 수단입니다. 취소가 서버에서 이미 실행한 작업을 되돌렸다고 가정하지 않습니다. 테스트에서는 A·B Promise를 원하는 순서로 완료시켜 성공과 실패 양쪽의 오래된 응답이 무시되는지 확인합니다.

## 검증

B 성공 뒤 A 성공, B 성공 뒤 A 실패, 최신 요청 실패, 실패 후 재시도를 검사합니다. 실제 시간을 기다리기보다 수동 완료 가능한 Promise로 순서를 제어합니다. 요청 무시와 취소는 구분하며 취소가 서버 작업까지 되돌린다고 가정하지 않습니다.

## 면접에서 말하기

> “기간 제목과 데이터가 같은 요청에 속한다는 불변식을 먼저 지키겠습니다. 이전 요청의 성공과 실패 모두 화면 변경 권한을 제거하고 역순 응답으로 재현하겠습니다.”

**꼬리질문:** debounce를 넣으면 해결되는가?

**해설:** 요청 수를 줄일 수 있지만 이미 시작된 요청의 순서 문제는 해결하지 않습니다. 응답 적용 대상 식별이 필요합니다.
