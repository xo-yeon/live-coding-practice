# Ads 운영툴 해설형 예상 문제 12선

전체 내용을 한 번에 복사하려면 [통합 학습 노트](ADS-STUDY-GUIDE.md)를 사용하세요. 01~12와 면접 가이드 외에 13~16장에 Frontend Fundamentals·선언적 UI·비동기 오류 복구·추상화 기준, 추가 모의 과제와 꼬리질문을 담았습니다. 추가 과정의 본문은 통합 노트에서 관리합니다.

이 자료는 토스 Ads 지원을 위한 **자체 제작 예상 문제**입니다. 실제 기출이나 내부 평가표를 확보한 자료가 아닙니다. 금융 광고 운영 대시보드라는 가상의 제품을 사용하고, 금액·권한·심사·상태 전환 정책은 각 문제의 학습용 계약입니다. 실제 토스 정책이나 금융상품의 규제를 나타내지 않습니다.

## 공개 자료에서 확인한 것과 학습을 위해 정한 것

2026-09-27 확인: 토스 공식 기술 글은 광고주 대시보드의 캠페인·예산·성과 관리와 계층형 데이터 탐색을 설명합니다. 데이터 규모와 요구에 따라 서버·브라우저·Worker 중 처리 위치를 결정하는 사례입니다. 이것은 업무 맥락의 근거이며 면접 출제 방식의 근거는 아닙니다. [토스 기술 글, 2026-08-20](https://toss.tech/article/ads_dashboard_fe)

토스 비즈니스 공개 페이지도 광고 타겟팅과 성과 리포트를 소개합니다. 따라서 금액과 지표를 정확히 보여주고, 운영자가 변경 결과를 믿을 수 있게 만드는 주제로 학습을 확장했습니다. [토스 비즈니스](https://business.toss.im/)

아래 카드·대출 광고 이름은 소재를 이해하기 위한 가상의 이름입니다. 고객의 실제 자산·소득·계좌 정보를 처리하지 않습니다. Ads의 범위가 금융상품 광고에만 한정된다는 뜻도 아닙니다.

## 이 교재가 다루는 화면

가상의 운영자는 광고 계정을 고르고, 캠페인 목록에서 성과를 확인한 뒤, 예산을 수정하거나 광고를 시작·중지합니다. 필요하면 기간별 보고서를 내려받습니다. 12개 문서는 이 흐름에서 데이터가 잘못 표시되거나 다른 대상에 저장되는 상황을 각각 설명합니다.

캠페인은 광고를 관리하는 단위이고 소재는 사용자에게 보여줄 이미지·문구 같은 광고 콘텐츠입니다. 이 교재에서는 개념을 익히기 위한 최소 관계만 사용합니다. 실제 서비스마다 캠페인·그룹·소재의 계층과 정책은 다를 수 있습니다.

## 반복해서 나오는 용어

| 용어 | 이 교재에서의 뜻 | 구체적인 예 |
| --- | --- | --- |
| 계약 | 요청·응답·실패·표시를 어떻게 해석할지 정한 규칙 | 성과 행이 없으면 0이 아니라 미집계 |
| 상태 원본 | 같은 정보가 여러 곳에 있을 때 판단의 기준으로 삼는 값 | URL에서 필터와 페이지를 읽어 화면 구성 |
| 정규화 | 허용값과 기본값을 적용해 조건을 일관되게 만드는 것 | 잘못된 page는 1로 처리 |
| 캐시 | 이전에 받은 데이터를 다시 쓰기 위해 보관하는 공간 | A 계정 목록을 계정별 key에 저장 |
| 초안 / 확정값 | 입력 중인 값 / 서버가 저장을 확인한 값 | 입력 15만원, 마지막 저장값 10만원 |
| 소유권 | 데이터·초안·응답이 어느 대상에 속하는지 | A 저장 응답은 B 화면에 적용하지 않음 |
| 불변식 | 처리 순서가 달라져도 항상 지켜야 할 조건 | 제목의 기간과 숫자의 기간이 같아야 함 |
| 원자성 | 관련 처리가 중간에 분리되지 않고 하나로 적용되는 성질 | 버전 확인과 조건부 저장을 함께 처리 |
| 멱등성 | 같은 요청을 반복해도 의도한 효과가 중복되지 않는 성질 | 중지 상태로 다시 설정해도 중지 유지 |
| 스냅샷 | 특정 시점의 조건이나 데이터를 고정한 사본 | 내보내기 클릭 당시의 기간·필터 |
| 재현 | 특정 조작과 입력으로 문제를 다시 발생시키는 것 | A 조회를 늦추고 B 응답부터 완료 |
| 회귀 검증 | 수정 때문에 기존 동작이 망가지지 않았는지 확인 | 충돌을 고친 뒤 정상 저장도 확인 |

원자성과 멱등성은 다릅니다. ‘세 광고를 모두 중지하거나 아무것도 바꾸지 않음’은 원자성이고, ‘같은 광고의 중지 요청을 반복해도 효과가 중복되지 않음’은 멱등성입니다. Promise 도구만 바꿔서는 서버의 원자성이나 멱등성을 만들 수 없습니다.

## 문서와 코드를 읽는 방법

각 문서는 개념 설명, 요구사항과 Before, 재현과 사용자 영향, After와 상세 해설, 검증, 면접 답변 순서로 읽습니다. Before는 왜 문제가 생기는지 관찰할 코드이고 After는 특정 전제에서 이를 개선하는 코드입니다. 면접 답변은 이해한 뒤 설명을 정리하는 예시이며 외울 정답 문장이 아닙니다.

코드의 `api`, `Campaign`, `Props`, 상태 setter, 오류 판별 함수는 주변 앱이 제공한다고 가정합니다. `api`는 이 저장소 전체에서 하나의 확정된 SDK를 뜻하지 않습니다. 문서별로 입력과 실패 계약을 설명하기 위한 이름입니다. 코드 블록 전체를 한 파일에 붙여 실행하는 방식으로 설계한 자료는 아닙니다.

예를 들어 `isConflict`는 409 충돌을 판별하고, `isExplicitRejection`은 서버가 변경 미적용을 보장한 오류를 판별합니다. 두 함수를 단순히 ‘오류가 있으면 true’로 구현하면 설명한 구분이 사라집니다. 단위 함수 테스트가 통과해도 계정 권한·DB 저장 원자성·실제 UI까지 검증된 것은 아닙니다.

## 공부 순서

1. 01·02·09: 숫자와 데이터의 의미를 먼저 익힙니다.

새 문제로 넘어갈 기준은 코드를 안 보고 외울 수 있는지가 아닙니다. 재현 조건을 스스로 정하고, 원인과 대안을 설명하며, 조건 하나가 바뀌었을 때 해결법도 바꿀 수 있는지 확인합니다.
