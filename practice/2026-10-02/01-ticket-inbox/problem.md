# 지원 요청함

Level 2 · 권장 코딩 35분 · 작업 파일 3개. 처음에는 시간 제한 없이 연습해도 됩니다. 사전 코드 읽기와 아래 테스트 학습 10~15분은 코딩 시간과 별개입니다.

## 상황

고객 지원팀이 요청 제목을 검색하고, 진행 상태를 확인하고, 요청을 완료하거나 다시 엽니다. 데이터는 브라우저 안의 연습용 목록이며 서버 저장은 없습니다.

## 요구사항

- 제목 검색은 앞뒤 공백을 무시하고 대소문자를 구분하지 않습니다. 빈 검색어는 전체 제목을 대상으로 합니다.
- 상태 필터는 전체·진행 중·완료이며 검색어와 함께 적용됩니다.
- 각 요청의 버튼으로 진행 중과 완료 상태를 바꿉니다. 현재 필터에 맞는 목록은 변경 직후 갱신됩니다.
- 상단의 전체 요청 수와 진행 중 요청 수는 검색·필터와 무관하게 전체 목록 기준입니다.
- 결과가 없으면 빈 결과 안내를 표시합니다. 요청 추가·삭제, 서버 동기화, 정렬은 범위 밖입니다.
- 외부 라이브러리 추가 없이 `working`만 수정하고 필요한 테스트를 직접 추가하세요.

## 파일과 실행

`working/TicketInbox.tsx` → `tickets.ts` → `TicketList.tsx` 순서로 읽어보세요. `before`는 원본, `working`은 수정 대상, `notes.md`는 분석 기록, `review.md`는 면접 후 기록입니다.

```bash
pnpm dev
pnpm vitest run practice/2026-10-02/01-ticket-inbox/tests
pnpm typecheck
pnpm lint
```

화면: http://localhost:5173/practice/tickets

공개 테스트는 시작 코드에서도 통과하는 기본 확인용이며 전체 요구사항을 보장하지 않습니다.

## 테스트 작성 학습

작은 별도 예제에서 **준비 → 행동 → 기대 결과**를 먼저 연습합니다. 예를 들어 `const items = ['a', 'b']`를 준비하고, `items.filter((item) => item === 'a')`를 실행한 뒤, 결과가 `['a']`인지 `expect(...).toEqual(['a'])`로 확인합니다. 이는 이 문제의 테스트 정답이 아닙니다.

전체 코드를 설명하고 문제를 파악한 다음, 공개 요구사항 중 발견한 문제 하나의 기대 동작을 말로 정하세요. `tests/challenge.test.tsx`에 직접 재현 테스트를 추가해 수정 전에는 그 문제 때문에 실패하는지 확인합니다. 수정 후 같은 테스트를 통과시키고, 관련 경계 사례 하나를 더 검증하세요. 내부 state 모양보다 사용자에게 보이는 결과를 검사하세요.

면접에서는 코드의 역할과 입력·출력, 동작 흐름, 발견한 문제와 사용자 영향, 수정 우선순위, 해결·검증 방안을 먼저 한 번에 설명합니다.
