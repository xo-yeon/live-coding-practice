## 항목별 상세 내역

* **발견 문제**:
  1. `selectedIds.push/splice`로 배열을 직접 변경하여 동일한 참조로 `setState` 호출 시 화면이 리렌더링되지 않는 문제 (정상 발견 및 수정)
  2. `selectVisible`이 기존 선택을 고려하지 않고 현재 검색 결과로 덮어써 이전 선택이 유실되는 문제 (정상 발견 및 수정)
* **누락 문제**: 없음
* **오판 문제**: 없음
* **잘한 수정**:
  - `new Set([...selectedIds, ...visible.map((item) => item.id)])`를 활용해 기존 선택 유지 및 중복 없는 합집합 처리.
  - 공개 테스트에 체크 즉시 반영과 검색어 변경 후 누적 카운트 검증 테스트 추가.
* **과도한 수정**: 없음 (최소한의 변경으로 핵심 요구사항 해결)
* **좋은 설명**:
  - 대규모 데이터에서 `array.includes()`의 $O(N)$ 탐색 비용과 `Set.has()`의 $O(1)$ 시간 복잡도 비교 설명이 매우 명확하고 훌륭함.
* **부족한 근거**:
  - React 상태 변경 감지 메커니즘을 "깊은 비교"로 설명했던 점 (React는 항상 `Object.is`를 통한 얕은 참조 비교만 수행함).

## 면접 중 진행된 질문·답변 및 피드백 내용

### 1. React 상태 비교 메커니즘과 불변성(Immutability)
- **질문**: React가 상태 변경 감지 시 얕은 비교(`Object.is`)를 채택한 이유와, 상태를 직접 수정하지 않고 불변성을 유지해야 하는 구체적인 이유는 무엇인가요?
- **지원자 답변**: 빠른 렌더링을 위해서이며, 불변성을 유지하지 않고 쉽게 상태가 변경되는 환경이라면 예상치 못한 에러나 결과가 발생할 확률이 높아지기 때문입니다.
- **면접관 피드백**:
  - **정확한 부분**: $O(1)$ 빠른 참조 비교를 통한 성능 확보, 사이드 이펙트 방지라는 핵심 방향을 정확히 파악함.
  - **보완 내용**: 재귀 순회(깊은 비교)는 $O(N)$ 비용으로 렌더링 병목을 유발하므로 얕은 비교를 채택함. 불변성을 지켜야 이전 렌더링 스냅샷 보존, 순수성 유지, `React.memo` 및 의존성 비교 최적화가 정상 작동함.

### 2. 불변성을 유지하는 코드 작성과 함수형 업데이트
- **질문**: `toggle` 함수에서 `push`/`splice` 없이 순수 불변성을 유지하려면 어떻게 작성해야 하며, `setSelectedIds((prev) => ...)`는 어떤 상황에서 필요한가요?
- **지원자 답변**: 새로운 변수로 새 배열을 만들어 업데이트할 수 있습니다. 함수형 업데이트는 기존 값에서 변동이 필요할 때 사용합니다.
- **면접관 피드백**:
  - **보완 내용**: `filter`와 전개 연산자를 결합(`prev.includes(id) ? prev.filter(x => x !== id) : [...prev, id]`)하여 원본 배열을 훼손하지 않는 비파괴적 패턴 권장.
  - 함수형 업데이트는 단순 변동 시점보다는 **상태 업데이트 배치(Batching)**나 비동기 콜백/이벤트 핸들러 내에서 **클로저의 오래된 상태(Stale State)를 방지하고 항상 최신 상태를 보장**해야 할 때 필수적임.

### 3. 대규모 데이터 처리와 자료구조 최적화
- **질문**: 받는 분 목록이 수천 명 이상일 때 `selectedIds.includes(item.id)` 방식의 성능 문제와 개선 방안은 무엇인가요?
- **지원자 답변**: `array.includes()`의 시간 복잡도는 $O(N)$으로 데이터가 많을 때 큰 비용이 듭니다. 따라서 시간 복잡도가 $O(1)$인 `Set.has()`를 이용하면 비용 측면에서 효율적으로 개선할 수 있습니다.
- **면접관 피드백**: 완벽한 정답. 렌더 루프 전체 비용이 $O(N \times M)$에서 $O(N)$으로 개선되며, 렌더링 시 `useMemo`로 `Set`을 파생하거나 상태 자체를 `Set`으로 설계하는 실무 패턴을 함께 고려할 수 있음.
